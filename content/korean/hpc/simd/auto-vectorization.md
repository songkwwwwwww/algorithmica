SIMD 병렬 처리는 대부분 *매우 병렬적인(embarrassingly parallel)* 계산에 사용됩니다. 즉, 배열의 모든 요소에 어떤 요소별(elementwise) 함수를 적용하고 결과를 다른 곳에 다시 쓰는 유형의 계산입니다. 이러한 환경에서는 SIMD가 어떻게 작동하는지 알 필요조차 없습니다. 컴파일러가 이러한 루프를 스스로 최적화할 수 있기 때문입니다. 단지 이러한 최적화가 존재하며, 일반적으로 5~10배의 속도 향상을 가져온다는 사실만 알고 있으면 됩니다.

아무것도 하지 않고 자동 벡터화에 의존하는 것이 사실 SIMD를 사용하는 가장 대중적인 방법입니다. 실제로 많은 경우, 단순성과 유지보수성을 위해 평범한 스칼라 코드를 유지하는 것이 권장되기도 합니다.

하지만 자동 벡터화가 가능해 보이는 루프도 기술적인 세부 사항 때문에 최적화되지 않는 경우가 많습니다. [다른 많은 사례](/hpc/compilation/contracts)와 마찬가지로, 정적 분석으로 유추할 수 있는 것보다 프로그래머가 문제에 대해 더 많이 알고 있을 수 있으므로 컴파일러는 프로그래머로부터 추가적인 입력을 필요로 할 수 있습니다.

### 잠재적인 문제들

우리가 [시작할 때](../intrinsics/#simd-intrinsics) 살펴보았던 "a + b" 예제를 다시 생각해 봅시다.

```c++
void sum(int *a, int *b, int *c, int n) {
    for (int i = 0; i < n; i++)
        c[i] = a[i] + b[i];
}
```

컴파일러의 입장이 되어 이 루프가 벡터화될 때 무엇이 잘못될 수 있는지 생각해 봅시다.

**배열 크기.** 배열 크기를 미리 알 수 없는 경우, 벡터화가 이득이 될 만큼 배열이 크지 않을 수 있습니다. 충분히 크더라도 루프의 남은 부분을 스칼라로 처리하기 위해 추가적인 체크가 필요하며, 이는 분기 비용을 발생시킵니다.

이러한 런타임 체크를 없애려면 컴파일 타임 상수인 배열 크기를 사용하고, 가급적 배열을 SIMD 블록 크기의 배수에 맞춰 패딩(padding)하는 것이 좋습니다.

**메모리 에일리어싱(Memory aliasing).** 배열 크기 문제가 없더라도 이 루프를 벡터화하는 것이 기술적으로 항상 옳은 것은 아닙니다. 예를 들어, 배열 `a`와 `c`가 시작 지점이 한 칸 차이 나도록 겹칠 수 있습니다. 프로그래머가 이런 식으로 컨볼루션을 통해 피보나치 수열을 계산하고 싶어 했을 수도 있기 때문입니다. 이 경우 SIMD 블록 내의 데이터가 겹치게 되어 실행 결과가 스칼라 케이스와 달라질 수 있습니다.

컴파일러가 함수가 겹치는 배열에 사용되지 않을 것임을 증명할 수 없는 경우, 벡터화된 버전과 "안전한" 버전이라는 두 가지 구현을 생성하고 런타임에 둘 중 하나를 선택하는 체크 코드를 삽입해야 합니다. 이를 피하기 위해 `__restrict__` 키워드를 추가하여 메모리 겹침이 없음을 컴파일러에 알릴 수 있습니다.

```cpp
void add(int * __restrict__ a, const int * __restrict__ b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

SIMD에 특화된 다른 방법으로는 "벡터 의존성 무시(ignore vector dependencies)" 프라그마(pragma)가 있습니다. 이는 루프 반복 사이에 의존성이 없음을 컴파일러에 알리는 일반적인 방법입니다.

```c++
#pragma GCC ivdep
for (int i = 0; i < n; i++)
    // ...
```

**정렬(Alignment).** 컴파일러는 또한 이 배열들의 정렬 상태를 알지 못하므로, 벡터화된 섹션을 시작하기 전에 배열 시작 부분의 일부 요소를 처리하거나 [비정렬 메모리 액세스(unaligned memory accesses)](../moving)를 사용하여 성능 손실을 감수해야 할 수도 있습니다.

컴파일러가 이러한 예외 케이스를 제거하도록 돕기 위해, 정적 배열에는 `alignas` 지정자를 사용하고 포인터에는 `std::assume_aligned` 함수를 사용하여 정렬되었음을 표시할 수 있습니다.

**벡터화 여부 확인.** 어떤 경우든 컴파일러가 의도한 대로 루프를 벡터화했는지 확인하는 것이 유용합니다. [어셈블리로 컴파일](/hpc/compilation/stages)하여 "v"로 시작하는 명령 블록을 찾거나, `-fopt-info-vec-optimized` 컴파일러 플래그를 추가하여 자동 벡터화가 일어나는 위치와 사용 중인 SIMD 너비를 확인할 수 있습니다. `optimized`를 `missed`나 `all`로 바꾸면 다른 곳에서 벡터화가 일어나지 않는 이유를 알 수도 있습니다.

컴파일러에게 의도를 정확히 전달하는 [다른 많은 방법](https://software.intel.com/sites/default/files/m/4/8/8/2/a/31848-CompilerAutovectorizationGuide.pdf)들이 있지만, 특히 복잡한 경우(예: 루프 내부에 분기나 함수 호출이 많은 경우)에는 추상화 수준을 한 단계 낮춰 수동으로 벡터화하는 것이 더 쉽습니다.

### SPMD

자동 벡터화와 수동 SIMD 인트린직(intrinsics) 사용 사이에는 "단일 프로그램, 다중 데이터(single program, multiple data, SPMD)"라는 깔끔한 절충안이 있습니다. 이는 프로그래머가 일반적인 직렬 프로그램처럼 코드를 작성하지만, 실제로는 하드웨어에서 병렬로 실행되는 계산 모델입니다.

프로그래밍 경험은 거의 동일하며 계산이 데이터 병렬적이어야 한다는 근본적인 제약은 여전하지만, SPMD는 컴파일러나 대상 CPU 아키처에 관계없이 벡터화가 일어날 것임을 보장합니다. 또한 여러 코어에 걸쳐 계산을 자동으로 병렬화할 수 있으며, 경우에 따라 다른 유형의 병렬 하드웨어로 오프로드(offload)할 수도 있습니다.

일부 현대적인 언어([Julia](https://docs.julialang.org/en/v1/base/base/#Base.SimdLoop.@simd)), 멀티프로세싱 API([OpenMP](https://www.openmp.org/spec-html/5.0/openmpsu42.html)), 전문 컴파일러(Intel [ISPC](https://ispc.github.io/))에서 SPMD를 지원하지만, 문제와 하드웨어가 모두 대규모 병렬 방식인 GPU 프로그래밍 분야에서 가장 큰 성공을 거두었습니다.

이 계산 모델에 대해서는 파트 2에서 훨씬 더 자세히 다룰 것입니다.
