SIMD를 사용하는 가장 저수준의 방법은 어셈블리 벡터 명령을 직접 사용하는 것이지만(스칼라 명령과 크게 다르지 않습니다), 우리는 그렇게 하지 않을 것입니다. 대신 최신 C/C++ 컴파일러에서 제공하는, 이러한 명령에 매핑되는 *인트린직(intrinsic)* 함수를 사용할 것입니다.

이 섹션에서는 인트린직 구문의 기초를 살펴보고, 이 장의 나머지 부분에서는 이를 광범위하게 사용하여 실제로 흥미로운 작업들을 수행해 볼 것입니다.

## 준비 작업

x86 인트린직을 사용하려면 약간의 기초 작업이 필요합니다.

먼저, 하드웨어에서 어떤 확장 기능이 지원되는지 확인해야 합니다. 리눅스에서는 `cat /proc/cpuinfo`를 호출하면 되고, 다른 플랫폼에서는 [WikiChip](https://en.wikichip.org/wiki/WikiChip)에서 CPU 이름을 검색하여 확인하는 것이 좋습니다. 어떤 경우든 지원되는 모든 벡터 확장 코드이 나열된 `flags` 섹션이 있을 것입니다.

또한 특정 벡터 확장 지원 여부를 포함하여 CPU에 대한 다양한 정보를 쿼리할 수 있는 특수 [CPUID](https://en.wikipedia.org/wiki/CPUID) 어셈블리 명령이 있습니다. 이는 주로 런타임에 정보를 얻어 각 마이크로아키텍처별로 별도의 바이너리를 배포하지 않도록 하는 데 사용됩니다. 출력 정보는 기능 마스크(feature mask) 형태로 매우 조밀하게 반환되므로, 컴파일러는 이를 이해하기 쉽게 만드는 내장 메서드를 제공합니다. 다음은 그 예입니다.

```c++
#include <iostream>
using namespace std;

int main() {
    cout << __builtin_cpu_supports("sse") << endl;
    cout << __builtin_cpu_supports("sse2") << endl;
    cout << __builtin_cpu_supports("avx") << endl;
    cout << __builtin_cpu_supports("avx2") << endl;
    cout << __builtin_cpu_supports("avx512f") << endl;

    return 0;
}
```

둘째, 필요한 인트린직 하위 집합이 포함된 헤더 파일을 포함해야 합니다. GCC의 `<bits/stdc++.h>`와 유사하게 모든 인트린직을 포함하는 `<x86intrin.h>` 헤더가 있으므로 이를 사용하겠습니다.

마지막으로, 대상 CPU가 실제로 이러한 확장 기능을 지원함을 [컴파일러에게 알려야 합니다](/hpc/compilation/flags). 이는 [이전에 했던 것처럼](../) `#pragma GCC target(...)`을 사용하거나, 컴파일러 옵션에서 `-march=...` 플래그를 사용하여 수행할 수 있습니다. 코드를 컴파일하고 실행하는 기계가 동일하다면 `-march=native`를 설정하여 마이크로아키텍처를 자동 감지하도록 할 수 있습니다.

이후의 모든 코드 예제는 다음 라인으로 시작한다고 가정합니다.

```c++
#pragma GCC target("avx2")
#pragma GCC optimize("O3")

#include <x86intrin.h>
#include <bits/stdc++.h>

using namespace std;
```

이 장에서는 현재 데스크톱 및 서버 컴퓨터의 95%에서 사용할 수 있는 AVX2 및 이전 SIMD 확장에 중점을 둘 것입니다. 하지만 일반적인 원칙은 AVX512, Arm Neon 및 기타 SIMD 아키텍처에도 동일하게 적용됩니다.

### SIMD 레지스터

SIMD 확장 간의 가장 눈에 띄는 차이점은 더 넓은 레지스터 지원 여부입니다.

- SSE (1999): `xmm0`부터 `xmm15`까지 16개의 128비트 레지스터 추가.
- AVX (2011): `ymm0`부터 `ymm15`까지 16개의 256비트 레지스터 추가.
- AVX512 (2017): `zmm0`부터 `zmm15`까지 16개의 512비트 레지스터 추가[^mask].

[^mask]: AVX512는 또한 마스킹 및 데이터 블렌딩에 사용되는 `k0`부터 `k7`까지 8개의 소위 *마스크 레지스터*를 추가했습니다. 여기서는 다루지 않으며 주로 AVX2 및 이전 표준을 사용합니다.

이름에서 짐작할 수 있듯이, 그리고 512비트가 이미 전체 캐시 라인을 차지한다는 사실로 볼 때, x86 설계자들은 조만간 더 넓은 레지스터를 추가할 계획이 없습니다.

C/C++ 컴파일러는 이러한 레지스터에 저장된 데이터를 참조하는 특수 *벡터 타입*을 구현합니다.

- 128비트: 단정밀도 부동 소수점용 `__m128`, 배정밀도 부동 소수점용 `__m128d`, 다양한 정수 데이터용 `__m128i`.
- 256비트: `__m256`, `__m256d`, `__m256i`.
- 512비트: `__m512`, `__m512d`, `__m512i`.

레지스터 자체는 모든 종류의 데이터를 담을 수 있으며, 이러한 타입들은 타입 체크용으로만 사용됩니다. 벡터 변수를 다른 벡터 타입으로 변환하는 것은 일반적인 타입 변환과 동일하며 비용이 들지 않습니다.

### SIMD 인트린직

*인트린직*은 단순히 이러한 벡터 데이터 타입으로 무언가를 수행하는 C 스타일 함수로, 대개 연결된 어셈블리 명령을 단순히 호출하는 방식입니다.

예를 들어, 다음은 AVX 인트린직을 사용하여 두 개의 64비트 부동 소수점 배열을 더하는 루프입니다.

```c++
double a[100], b[100], c[100];

// 4개씩 블록 단위로 반복합니다.
// 256비트 레지스터에는 4개의 double이 들어갈 수 있기 때문입니다.
for (int i = 0; i < 100; i += 4) {
    // 256비트 세그먼트 두 개를 레지스터로 로드합니다.
    __m256d x = _mm256_loadu_pd(&a[i]);
    __m256d y = _mm256_loadu_pd(&b[i]);

    // 4+4개의 64비트 숫자를 더합니다.
    __m256d z = _mm256_add_pd(x, y);

    // 256비트 결과를 c[i]부터 시작하는 메모리에 씁니다.
    _mm256_storeu_pd(&c[i], z);
}
```

SIMD 사용의 주요 과제는 데이터를 레지스터 로드에 적합한 연속적이고 고정된 크기의 블록으로 구성하는 것입니다. 위의 코드에서 배열 길이가 블록 크기로 나누어떨어지지 않으면 문제가 될 수 있습니다. 이에 대한 두 가지 일반적인 해결책이 있습니다.

1. 마지막 불완전한 세그먼트까지 반복하여 "초과(overshoot)"하는 방식입니다. 소유하지 않은 메모리 영역을 읽거나 써서 세그먼트 폴트(segfault)가 발생하지 않도록, 배열을 가장 가까운 블록 크기로 패딩(보통 0과 같은 "중립" 요소로)해야 합니다.
2. 반복을 한 번 덜 수행하고, 마지막에 남은 부분은 일반적인 스칼라 연산으로 계산하는 작은 루프를 작성하는 방식입니다.

사람은 더 간단하고 코드가 적게 드는 1번 방식을 선호하고, 컴파일러는 다른 합법적인 선택지가 없기 때문에 2번 방식을 선호합니다.

### 명령 참조

대부분의 SIMD 인트린직은 `_mm<크기>_<동작>_<타입>`과 유사한 명명 규칙을 따르며, 유사한 이름의 단일 어셈블리 명령에 대응됩니다. 어셈블리 명명 규칙에 익숙해지면 비교적 자명해 보이지만, 가끔은 고양이가 키보드 위를 걸어 다니며 이름을 지은 것 같기도 합니다(이걸 설명해 보세요: [punpcklqdq](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html#ig_expand=3037,3009,4870,4870,4872,4875,833,879,874,849,848,6715,4845,6046,3853,288,6570,6527,6527,90,7307,6385,5993,2692,6946,6949,5456,6938,5456,1021,3007,514,518,4875,7253,7183,3892,5135,5260,5259,6385,3915,4027,3873,7401&techs=AVX,AVX2&text=punpcklqdq)).

이해를 돕기 위한 몇 가지 예제입니다.

- `_mm_add_epi16`: 16비트 *확장 패킹 정수(extended packed integers)*, 즉 `short` 타입의 128비트 벡터 두 개를 더합니다.
- `_mm256_acos_pd`: 4개의 *패킹된 double*에 대해 요소별 $\arccos$를 계산합니다.
- `_mm256_broadcast_sd`: 메모리 위치의 `double` 하나를 결과 벡터의 모든 4개 요소로 브로드캐스트(복사)합니다.
- `_mm256_ceil_pd`: 4개의 `double` 각각을 가장 가까운 정수로 올림합니다.
- `_mm256_cmpeq_epi32`: 8+8개의 패킹된 `int`를 비교하고, 동일한 요소 쌍에 대해 1을 포함하는 마스크를 반환합니다.
- `_mm256_blendv_ps`: 마스크에 따라 두 벡터 중 하나에서 요소를 선택합니다.

짐작하셨겠지만 인트린직의 수는 조합론적으로 매우 많으며, 일부 명령에는 즉시값(immediate values)도 포함되어 있어 인트린직에 컴파일 타임 상수 매개변수가 필요하기도 합니다. 예를 들어 부동 소수점 비교 명령은 [32개의 서로 다른 수정자](https://stackoverflow.com/questions/16988199/how-to-choose-avx-compare-predicate-variants)를 가집니다.

어떤 이유에서인지 레지스터에 저장된 데이터 타입과는 무관하지만 특정 벡터 타입(주로 32비트 float)만 받는 연산들도 있습니다. 이러한 인트린직을 사용하려면 해당 타입으로 변환했다가 다시 되돌려야 합니다. 이 장의 예제를 단순화하기 위해 주로 256비트 AVX2 레지스터의 32비트 정수(`epi32`)를 다룰 것입니다.

x86 SIMD 인트린직에 대한 매우 유용한 참조 자료는 [Intel Intrinsics Guide](https://software.intel.com/sites/landingpage/IntrinsicsGuide/)입니다. 카테고리 및 확장별 그룹화, 설명, 의사 코드, 관련 어셈블리 명령, 그리고 인텔 마이크로아키텍처에서의 레이턴시(latency)와 처리량(throughput) 정보가 포함되어 있습니다. 이 페이지를 즐겨찾기 해두는 것이 좋습니다.

인텔 가이드는 특정 명령이 존재함을 알고 그 이름이나 성능 정보를 찾고 싶을 때 유용합니다. 명령의 존재 여부조차 모를 때는 이 [치트 시트(cheat sheet)](https://db.in.tum.de/~finis/x86%20intrinsics%20cheat%20sheet%20v1.0.pdf)가 더 도움이 될 수 있습니다.

**명령 선택.** 컴파일러가 반드시 당신이 지정한 정확한 명령을 선택하는 것은 아닙니다. [이전에 논의한](/hpc/analyzing-performance/assembly) 스칼라 `c = a + b`와 유사하게 융합 벡터 덧셈(fused vector addition) 명령도 존재합니다. 따라서 루프 사이클당 2+1+1=4개의 명령을 사용하는 대신 컴파일러는 [위의 코드를 다음과 같이](https://godbolt.org/z/dMz8E5Ye8) 3개의 명령 블록으로 다시 작성합니다.

```nasm
vmovapd ymm1, YMMWORD PTR a[rax]
vaddpd  ymm0, ymm1, YMMWORD PTR b[rax]
vmovapd YMMWORD PTR c[rax], ymm0
```

드물지만 이러한 컴파일러의 간섭이 상황을 악화시키는 경우도 있으므로, 항상 [어셈블리를 확인](/hpc/compilation/stages)하고 생성된 벡터 명령("v"로 시작함)을 자세히 살펴보는 것이 좋습니다.

또한 일부 인트린직은 편리한 지름길로서 단일 명령이 아닌 짧은 명령 시퀀스에 매핑되기도 합니다. [브로드캐스트 및 추출(extract)](../moving#register-aliasing)이 대표적인 예입니다.

### GCC 벡터 확장

C 인트린직의 설계가 끔찍하다고 느껴진다면, 당신 혼자가 아닙니다. 저도 SIMD 코드를 작성하고 Intel Intrinsics Guide를 읽는 데 수백 시간을 보냈지만, 여전히 `_mm256`을 입력해야 하는지 `__m256`을 입력해야 하는지 헷갈릴 때가 있습니다.

인트린직은 사용하기 어려울 뿐만 아니라 이식성이나 유지보수성도 좋지 않습니다. 좋은 소프트웨어라면 각 CPU마다 서로 다른 프로시저를 유지하고 싶지 않을 것입니다. 아키처에 구애받지 않는 방식으로 한 번만 구현하고 싶을 것입니다.

어느 날 GNU 프로젝트의 컴파일러 엔지니어들도 같은 생각을 했고, 관련 명령에 맞게 일부 연산자가 오버로드된 배열처럼 느껴지는 자신만의 벡터 타입을 정의하는 방법을 개발했습니다.

GCC에서 256비트(32바이트) 레지스터에 패킹된 8개의 정수 벡터를 정의하는 방법은 다음과 같습니다.

```c++
typedef int v8si __attribute__ (( vector_size(32) ));
// 타입 ^   ^ 타입 이름          바이트 단위 크기 ^ 
```

안타깝게도 이는 C나 C++ 표준의 일부가 아니므로 컴파일러마다 구문이 다릅니다.

타입 이름에 요소의 크기와 타입을 포함하는 일종의 명명 규칙이 있습니다. 위의 예에서는 "8개의 부호 있는 정수 벡터(vector of 8 signed integers)"를 정의했습니다. 하지만 `vec`, `reg` 등 원하는 이름을 선택할 수 있습니다. 다만 `std::vector`와의 혼동을 피하기 위해 `vector`라는 이름은 피하는 것이 좋습니다.

이러한 타입을 사용하는 주요 장점은 관련 인트린직을 찾아보는 대신 일반적인 C++ 연산자를 많은 연산에 사용할 수 있다는 점입니다.

```c++
v4si a = {1, 2, 3, 5};
v4si b = {8, 13, 21, 34};

v4si c = a + b;

for (int i = 0; i < 4; i++)
    printf("%d\n", c[i]);

c *= 2; // 스칼라 곱셈

for (int i = 0; i < 4; i++)
    printf("%d\n", c[i]);
```

벡터 타입을 사용하면 이전에 인트린직으로 구현했던 "a + b" 루프를 크게 단순화할 수 있습니다.

```c++
typedef double v4d __attribute__ (( vector_size(32) ));
v4d a[100/4], b[100/4], c[100/4];

for (int i = 0; i < 100/4; i++)
    c[i] = a[i] + b[i];
```

보시다시피 벡터 확장은 인트린직 함수의 악몽에 비해 훨씬 깔끔합니다. 단점은 우리가 하고 싶은 작업 중 일부는 네이티브 C++ 구문으로 표현할 수 없어 여전히 인트린직이 필요하다는 점입니다. 다행히 이는 배타적인 선택이 아닙니다. 벡터 타입은 `_mm` 타입으로의 제로 비용 변환을 지원하기 때문입니다.

```c++
v8f x;
int mask = _mm256_movemask_ps((__m256) x)
```

또한 이식 가능한 SIMD 코드를 작성할 수 있는 유사한 기능을 제공하고 인트린직이나 내장 벡터 타입보다 사용하기 편리한 다양한 언어용 서드파티 라이브러리들이 있습니다. C++의 대표적인 예로는 [Highway](https://github.com/google/highway), [Expressive Vector Engine](https://github.com/jfalcou/eve), [Vector Class Library](https://github.com/vectorclass/version2), [xsimd](https://github.com/xtensor-stack/xsimd) 등이 있습니다.

잘 정립된 SIMD 라이브러리를 사용하면 개발자 경험이 크게 향상되므로 권장됩니다. 하지만 이 책에서는 하드웨어에 가깝게 유지하기 위해 주로 인트린직을 직접 사용하고, 단순함을 위해 가끔 벡터 확장을 병행할 것입니다.
