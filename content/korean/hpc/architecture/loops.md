조금 더 복잡한 예시를 살펴보겠습니다.

```nasm
loop:
    add  edx, DWORD PTR [rax]
    add  rax, 4
    cmp  rax, rcx
    jne  loop
```

이 코드는 단순한 `for` 루프처럼 32비트 정수 배열의 합을 계산합니다.

루프의 "몸체(body)"는 `add edx, DWORD PTR [rax]`입니다. 이 명령어는 반복자(iterator) `rax`로부터 데이터를 로드하여 누산기(accumulator) `edx`에 더합니다. 다음으로 `add rax, 4`를 통해 반복자를 4바이트 앞으로 이동시킵니다. 그런 다음 조금 더 복잡한 일이 일어납니다.

### 점프

어셈블리에는 고수준 언어가 가진 if, for, 함수 또는 기타 제어 흐름 구조가 없습니다. 대신 저수준 프로그래밍 세계에서 "점프(jump)"라고 알려진 `goto`가 있습니다.

**점프**는 명령어 포인터를 피연산자로 지정된 위치로 이동시킵니다. 이 위치는 메모리의 절대 주소일 수도 있고, 현재 주소에 대한 상대 주소일 수도 있으며, 심지어 [런타임 중에 계산](../indirect)될 수도 있습니다. 이러한 주소를 직접 관리하는 번거로움을 피하기 위해, 임의의 명령어에 문자열 뒤에 `:`를 붙여 표시할 수 있습니다. 이를 레이블(label)이라고 하며, 기계어로 변환될 때 이 명령어의 상대 주소로 대체됩니다.

레이블은 어떤 문자열이든 될 수 있지만, 컴파일러는 창의력을 발휘하지 않고 레이블 이름을 정할 때 [보통](https://godbolt.org/z/T45x8GKa5) 소스 코드의 줄 번호와 함수의 이름 및 시그니처를 사용합니다.

**무조건** 점프 `jmp`는 `while (true)`와 같은 루프를 구현하거나 프로그램의 부분들을 연결하는 데에만 사용될 수 있습니다. 실제 제어 흐름을 구현하는 데에는 **조건부** 점프 계열이 사용됩니다.

이러한 조건들이 프로그래밍 언어에서처럼 어딘가에서 `bool` 값으로 계산되어 조건부 점프의 피연산자로 전달된다고 생각하는 것이 합리적일 수 있습니다. 하지만 하드웨어에서는 그렇게 구현되지 않습니다. 조건부 연산은 특수한 `FLAGS` 레지스터를 사용하며, 먼저 어떤 종류의 체크를 수행하는 명령어를 실행하여 이 레지스터를 채워야 합니다.

위 예시에서 `cmp rax, rcx`는 반복자 `rax`를 배열 끝 포인터 `rcx`와 비교합니다. 이 연산은 `FLAGS` 레지스터를 업데이트하며, 이제 `jne loop`에서 이 레지스터의 특정 비트를 조회하여 두 값이 같은지 여부를 판단할 수 있습니다. 그 결과에 따라 다시 시작 부분으로 점프하거나 다음 명령어로 계속 진행하여 루프를 빠져나오게 됩니다.

### 루프 언롤링

위의 루프에서 한 가지 눈에 띄는 점은 단일 요소를 처리하는 데 오버헤드가 많다는 것입니다. 각 사이클 동안 유용한 명령어는 단 하나만 실행되고, 나머지 3개는 반복자를 증가시키고 루프가 끝났는지 확인하는 데 사용됩니다.

우리가 할 수 있는 일은 반복되는 단계들을 함께 그룹화하여 루프를 *언롤링(unroll)* 하는 것입니다. 이는 C 언어에서 다음과 같이 작성하는 것과 같습니다.

```c++
for (int i = 0; i < n; i += 4) {
    s += a[i];
    s += a[i + 1];
    s += a[i + 2];
    s += a[i + 3];
}
```

어셈블리에서는 다음과 같이 보일 것입니다.

```nasm
loop:
    add  edx, [rax]
    add  edx, [rax+4]
    add  edx, [rax+8]
    add  edx, [rax+12]
    add  rax, 16
    cmp  rax, rsi
    jne  loop
```

이제 4개의 유용한 명령어를 처리하는 데 3개의 루프 제어 명령어만 필요하게 되었습니다(효율성 측면에서 $\frac{1}{4}$에서 $\frac{4}{7}$로 개선됨). 이를 계속하여 오버헤드를 거의 0으로 줄일 수 있습니다.

실제로 루프 언롤링이 성능을 위해 항상 필요한 것은 아닙니다. 현대의 프로세서는 명령어를 하나씩 실행하지 않고 [보류 중인 명령어 큐(queue of pending instructions)](/hpc/pipelining)를 유지하여, 두 개의 독립적인 연산이 서로를 기다리지 않고 동시에 실행될 수 있기 때문입니다.

우리의 경우도 마찬가지입니다. 언롤링을 통한 실제 속도 향상은 4배에 미치지 못할 것입니다. 카운터를 증가시키고 완료 여부를 확인하는 작업은 루프 몸체와 독립적이므로, 몸체와 동시에 실행되도록 스케줄링될 수 있기 때문입니다. 하지만 여전히 어느 정도까지는 [컴파일러에게 언롤링을 요청](/hpc/compilation/situational)하는 것이 유익할 수 있습니다.

### 대안적인 접근 방식

조건부 점프를 만들기 위해 반드시 `cmp`나 이와 유사한 명령어를 명시적으로 사용할 필요는 없습니다. 다른 많은 명령어들이 `FLAGS` 레지스터를 읽거나 수정하며, 때로는 부수적으로 선택적인 예외 체크를 가능하게 합니다.

예를 들어, `add`는 결과가 0인지, 음수인지, 오버플로우나 언더플로우가 발생했는지 등을 나타내는 여러 플래그를 항상 설정합니다. 이러한 메커니즘을 활용하여 컴파일러는 종종 다음과 같은 루프를 생성합니다.

```nasm
    mov  rax, -100  ; 100을 배열 크기로 대체
loop:
    add  edx, DWORD PTR [rax + 100 + rcx]
    add  rax, 4
    jnz  loop       ; 결과가 0인지 확인
```

이 코드는 사람이 읽기에는 조금 더 어렵지만, 반복되는 부분에서 명령어가 하나 더 적으며, 이는 성능에 유의미한 영향을 미칠 수 있습니다.
