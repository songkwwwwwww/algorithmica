컴퓨터 엔지니어들은 [CPU 파이프라인](/hpc/pipelining)을 정신적으로 두 부분으로 나누는 것을 좋아합니다. 하나는 메모리에서 명령어를 가져와 해석하는 *프런트엔드(front-end)*이고, 다른 하나는 명령어를 스케줄링하고 최종적으로 실행하는 *백엔드(back-end)*입니다. 일반적으로 성능 병목 현상은 실행 단계에서 발생하며, 이러한 이유로 이 책의 대부분의 노력은 백엔드 최적화에 할애될 것입니다.

하지만 때때로 프런트엔드가 백엔드를 포화시킬 만큼 빠르게 명령어를 공급하지 못할 때 그 반대의 상황이 발생할 수 있습니다. 이는 여러 가지 이유로 발생할 수 있는데, 궁극적으로는 기계어가 메모리에 레이아웃되는 방식과 관련이 있습니다. 사용하지 않는 코드를 제거하거나, "if" 분기를 바꾸거나, 심지어 함수 선언 순서를 변경하는 것만으로도 성능이 향상되거나 저하되는 기이한 방식으로 성능에 영향을 미칩니다.

### CPU 프런트엔드

기계어가 명령어로 변환되어 CPU가 프로그래머의 의도를 이해하기 전에, 먼저 우리가 관심을 갖는 두 가지 중요한 단계인 *페치(fetch)*와 *디코드(decode)*를 거쳐야 합니다.

**페치(fetch)** 단계에서 CPU는 메인 메모리에서 고정된 크기의 바이트 덩어리를 로드합니다. 여기에는 여러 명령어의 이진 인코딩이 포함되어 있습니다. 이 블록 크기는 머신마다 다를 수 있지만 x86에서는 일반적으로 32바이트입니다. 중요한 점은 이 블록이 [정렬(aligned)](/hpc/cpu-cache/cache-lines)되어 있어야 한다는 것입니다. 즉, 덩어리의 주소는 그 크기(여기서는 32B)의 배수여야 합니다.

다음은 **디코드(decode)** 단계입니다. CPU는 이 바이트 덩어리를 보고 명령어 포인터 이전의 모든 것을 버리고 나머지를 명령어로 나눕니다. 기계어 명령어는 가변적인 바이트 수를 사용하여 인코딩됩니다. `inc rax`와 같이 단순하고 매우 일반적인 것은 1바이트를 차지하는 반면, 인코딩된 상수와 동작 수정 접두사가 있는 모호한 명령어는 최대 15바이트까지 차지할 수 있습니다. 따라서 32바이트 블록에서 가변적인 수의 명령어가 디코딩될 수 있지만, *디코드 폭(decode width)*이라고 불리는 머신에 따른 한계를 넘을 수는 없습니다. 제 CPU([Zen 2](https://en.wikichip.org/wiki/amd/microarchitectures/zen_2))에서 디코드 폭은 4입니다. 이는 각 사이클마다 최대 4개의 명령어가 디코딩되어 다음 단계로 전달될 수 있음을 의미합니다.

이 단계들은 파이프라인 방식으로 작동합니다. CPU가 다음에 필요한 명령어 블록이 무엇인지 판단(또는 [예측](/hpc/pipelining/branching/))할 수 있다면, 페치 단계는 현재 블록의 마지막 명령어가 디코딩될 때까지 기다리지 않고 즉시 다음 블록을 로드합니다.

### 코드 정렬

다른 조건이 같다면, 컴파일러는 일반적으로 기계어 코드가 더 짧은 명령어를 선호합니다. 이렇게 하면 단일 32B 페치 블록에 더 많은 명령어가 들어갈 수 있고 바이너리 크기도 줄어들기 때문입니다. 하지만 때때로 페치된 명령어 블록이 정렬되어야 한다는 사실 때문에 그 반대가 선호되기도 합니다.

32B 정렬된 블록의 마지막 바이트에서 시작하는 명령어 시퀀스를 실행해야 한다고 가정해 보십시오. 첫 번째 명령어는 추가 지연 없이 실행할 수 있겠지만, 후속 명령어의 경우 다른 명령어 페치를 수행하기 위해 한 사이클을 더 기다려야 합니다. 만약 코드 블록이 32B 경계에 정렬되어 있었다면, (명령어가 너무 길거나 상호 의존적이지 않은 한) 최대 4개의 명령어가 디코딩되어 동시에 실행될 수 있었을 것입니다.

이를 염두에 두고 컴파일러는 종종 해로워 보이는 최적화를 수행합니다. 때때로 기계어 코드가 더 긴 명령어를 선호하거나, 심지어 아무것도 하지 않는 더미 명령어[^nop]를 삽입하여 주요 점프 위치를 적절한 2의 거듭제곱 경계에 정렬시키기도 합니다.

[^nop]: 이러한 명령어를 no-op 또는 NOP 명령어라고 합니다. x86에서 아무것도 하지 않는 "공식적인 방법"은 `xchg rax, rax`(레지스터를 자기 자신과 교체)입니다. CPU는 이를 인식하고 디코드 단계를 제외하고는 실행하는 데 추가 사이클을 소비하지 않습니다. `nop` 단축어는 동일한 기계어 코드로 매핑됩니다.

GCC에서는 `-falign-labels=n` 플래그를 사용하여 특정 정렬 정책을 지정할 수 있으며, 더 선택적으로 지정하려면 `-labels`를 `-function`, `-loops` 또는 `-jumps`로 [대체](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)할 수 있습니다. `-O2` 및 `-O3` 최적화 수준에서는 기본적으로 활성화됩니다. 특정 정렬을 설정하지 않으면 머신에 따른 (보통 합리적인) 기본값을 사용합니다.

### 명령어 캐시

명령어는 하위 계층의 캐시가 별도의 *명령어 캐시(instruction cache)*로 대체된다는 점을 제외하고는 데이터와 거의 동일한 [메모리 시스템](/hpc/cpu-cache)을 사용하여 저장되고 페치됩니다(무작위 데이터 읽기가 이를 처리하는 코드를 쫓아내는 것을 원치 않기 때문입니다).

명령어 캐시는 다음과 같은 상황에서 매우 중요합니다.

- 다음에 어떤 명령어를 실행할지 몰라 [낮은 지연 시간(low latency)](/hpc/cpu-cache/latency)으로 다음 블록을 페치해야 할 때.
- 길지만 처리가 빠른 명령어 시퀀스를 실행 중이어서 [높은 대역폭(high bandwidth)](/hpc/cpu-cache/bandwidth)이 필요할 때.

따라서 메모리 시스템은 기계어 코드가 큰 프로그램의 병목 지점이 될 수 있습니다. 이러한 고려 사항은 이전에 논의한 최적화 기술의 적용을 제한합니다.

- [함수 인라이닝](../functions)이 항상 최적은 아닙니다. 코드 공유를 줄이고 바이너리 크기를 늘려 더 많은 명령어 캐시를 요구하기 때문입니다.
- [루프 언롤링](../loops)은 컴파일 타임에 반복 횟수를 알 수 있더라도 어느 정도까지만 유익합니다. 어느 시점에는 CPU가 메인 메모리에서 명령어와 데이터를 모두 가져와야 하며, 이 경우 메모리 대역폭에 의해 병목 현상이 발생할 가능성이 높습니다.
- 과도한 [코드 정렬](#코드-정렬)은 바이너리 크기를 늘려 다시 더 많은 명령어 캐시를 요구합니다. 페치에 한 사이클을 더 쓰는 것은 캐시 미스가 발생하여 메인 메모리에서 명령어가 페치되기를 기다리는 것에 비하면 사소한 페널티입니다.

또 다른 측면은 자주 사용되는 명령어 시퀀스를 동일한 [캐시 라인(cache lines)](/hpc/cpu-cache/cache-lines) 및 [메모리 페이지](/hpc/cpu-cache/paging)에 배치하면 [캐시 지역성(cache locality)](/hpc/external-memory/locality)이 향상된다는 점입니다. 명령어 캐시 활용도를 높이려면 핫 코드(hot code)는 핫 코드끼리, 콜드 코드(cold code)는 콜드 코드끼리 그룹화하고, 가능하다면 데드 코드(사용되지 않는 코드)를 제거해야 합니다. 이 아이디어를 더 자세히 알고 싶다면, 최근 LLVM에 [병합](https://github.com/llvm/llvm-project/commit/4c106cfdf7cf7eec861ad3983a3dd9a9e8f3a8ae)된 Facebook의 [Binary Optimization and Layout Tool (BOLT)](https://engineering.fb.com/2018/06/19/data-infrastructure/accelerate-large-scale-applications-with-bolt/)을 확인해 보시기 바랍니다.

### 불균등한 분기

어떤 이유로 정수 구간의 길이를 계산하는 헬퍼 함수가 필요하다고 가정해 봅시다. 이 함수는 $x$와 $y$ 두 인자를 받지만, 편의상 어느 쪽이 비어 있지 않은지에 따라 $[x, y]$ 또는 $[y, x]$에 해당할 수 있습니다. 순수 C에서는 아마도 다음과 같이 작성할 것입니다.

```c++
int length(int x, int y) {
    if (x > y)
        return x - y;
    else
        return y - x;
}
```

x86 어셈블리에서는 이를 구현하는 방법이 훨씬 다양하며 성능에 눈에 띄는 영향을 미칩니다. 이 코드를 어셈블리로 직접 매핑하는 것부터 시작해 보겠습니다.

```nasm
length:
    cmp  edi, esi
    jle  less
    ; x > y
    sub  edi, esi
    mov  eax, edi
done:
    ret
less:
    ; x <= y
    sub  esi, edi
    mov  eax, esi
    jmp  done
```

처음의 C 코드는 매우 대칭적으로 보이지만 어셈블리 버전은 그렇지 않습니다. 이로 인해 한 분기가 다른 분기보다 약간 더 빠르게 실행될 수 있다는 흥미로운 특징이 생깁니다. `x > y`인 경우 CPU는 `cmp`와 `ret` 사이의 5개 명령어만 실행하면 되며, 함수가 정렬되어 있다면 이들은 모두 한 번에 페치될 것입니다. 반면 `x <= y`인 경우 두 번의 점프가 더 필요합니다.

`x > y`인 경우가 *드물다*(누가 반전된 구간의 길이를 계산하겠습니까?)고 가정하는 것이 합리적일 수 있습니다. 이는 거의 발생하지 않는 예외에 가깝습니다. 이 케이스를 감지하고 단순히 `x`와 `y`를 바꿀 수 있습니다.

```c++
int length(int x, int y) {
    if (x > y)
        swap(x, y);
    return y - x;
}
```

else가 없는 if 패턴에서 일반적으로 그렇듯이 어셈블리는 다음과 같이 진행됩니다.

```nasm
length:
    cmp  edi, esi
    jle  normal     ; x <= y이면 스왑이 필요 없으므로 xchg를 건너뛸 수 있음
    xchg edi, esi
normal:
    sub  esi, edi
    mov  eax, esi
    ret
```

총 명령어 길이는 8에서 6으로 줄었습니다. 하지만 여전히 우리가 가정한 사례에 대해 완전히 최적화된 것은 아닙니다. `x > y`가 절대 일어나지 않는다고 생각한다면, 절대 실행되지 않을 `xchg edi, esi` 명령어를 로드하는 것은 낭비입니다. 이를 정상적인 실행 경로 밖으로 이동시켜 해결할 수 있습니다.

```nasm
length:
    cmp  edi, esi
    jg   swap
normal:
    sub  esi, edi
    mov  eax, esi
    ret
swap:
    xchg edi, esi
    jmp normal
```

이 기술은 일반적으로 예외 케이스를 처리할 때 매우 유용하며, 고수준 코드에서는 특정 분기가 다른 분기보다 더 일어날 가능성이 높다는 [힌트](/hpc/compilation/situational)를 컴파일러에게 줄 수 있습니다.

```c++
int length(int x, int y) {
    if (x > y) [[unlikely]]
        swap(x, y);
    return y - x;
}
```

이 최적화는 분기가 매우 드물게 발생하는 경우에만 유익합니다. 그렇지 않은 경우에는 코드 레이아웃보다 더 중요한 [다른 측면](/hpc/pipelining/hazards)이 있어 컴파일러가 분기를 아예 피하도록 강제합니다. 이 경우 분기를 특수한 "조건부 이동(conditional move)" 명령어로 대체하며, 이는 대략 삼항 연산식 `(x > y ? y - x : x - y)` 또는 `abs(x - y)` 호출에 해당합니다.

```nasm
length:
    mov   edx, edi
    mov   eax, esi
    sub   edx, esi
    sub   eax, edi
    cmp   edi, esi
    cmovg eax, edx  ; "edi > esi이면 이동"
    ret
```

분기를 제거하는 것은 중요한 주제이며, [다음 장의 상당 부분](/hpc/pipelining/branching)을 이를 더 자세히 논의하는 데 할애할 것입니다.
