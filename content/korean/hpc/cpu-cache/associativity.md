크기가 $N=2^{21}$인 배열에 대해 고정된 스텝 크기 256으로 반복하며 값을 증가시키는 루프를 생각해 보십시오:

```cpp
for (int i = 0; i < N; i += 256)
    a[i]++;
```

그리고 스텝 크기가 257인 다음 루프를 보십시오:

```cpp
for (int i = 0; i < N; i += 257)
    a[i]++;
```

어느 것이 더 빨리 끝날까요? 몇 가지 고려 사항이 떠오를 것입니다:

- 처음에는 별 차이가 없거나, 두 번째 루프가 총 반복 횟수가 적으므로 약 $\frac{257}{256}$배 정도 더 빠를 것이라고 생각할 수 있습니다.
- 그러다가 256이 깔끔한 숫자라는 점을 떠올리고, [SIMD](/hpc/simd)나 메모리 시스템과 관련이 있을 수 있으니 첫 번째 루프가 더 빠를 수도 있다고 생각할 수 있습니다.

하지만 정답은 매우 반직관적입니다. 두 번째 루프가 무려 10배나 더 빠릅니다.

이는 단지 하나의 나쁜 스텝 크기 때문만이 아닙니다. 큰 2의 거듭제곱의 배수인 모든 인덱스에서 성능이 저하됩니다:

![총 반복 횟수가 일정하도록 배열 크기를 정규화함](../img/strides-small.svg)

벡터화 같은 것은 없으며 두 루프는 스텝 크기를 제외하고 동일한 어셈블리를 생성합니다. 이 효과는 오로지 메모리 시스템, 특히 하드웨어에서 CPU 캐시가 구현되는 방식의 독특한 산물인 *캐시 연관성(cache associativity)*이라는 특징 때문입니다.

### 하드웨어 캐시 (Hardware Caches)

메모리 시스템을 [이론적으로](/hpc/external-memory) 공부했을 때, 소프트웨어에서 [캐시 교체 정책을 구현하는 다양한 방법](/hpc/external-memory/policies/)에 대해 논의했습니다. 우리가 집중했던 한 가지 전략은 *최근 최소 사용(least recently used, LRU)* 정책이었습니다. 이는 단순하고 효과적이지만 여전히 사소하지 않은 데이터 조작이 필요합니다.

하드웨어 맥락에서 이러한 방식은 *완전 연관 캐시(fully associative cache)*라고 불립니다. $M$개의 셀이 있고 각 셀은 총 $N$개의 메모리 위치 중 어디에나 대응하는 캐시 라인을 보관할 수 있습니다. 경합이 발생하면 가장 오랫동안 액세스되지 않은 라인이 쫓겨나고 새 라인으로 교체됩니다.

![완전 연관 캐시](../img/cache1.png)

완전 연관 캐시의 문제는 "수백만 개 중 가장 오래된 캐시 라인을 찾는" 작업을 소프트웨어로 구현하기는 꽤 어렵고 하드웨어로는 실행 불가능하다는 점입니다. 16개 정도의 항목을 가진 완전 연관 캐시는 만들 수 있지만, 수백 개의 캐시 라인을 관리하는 것은 비용이 너무 많이 들거나 너무 느려져서 가치가 없게 됩니다.

우리는 훨씬 더 간단한 다른 접근 방식을 사용할 수 있습니다. RAM의 각 64바이트 블록을 점유할 수 있는 단일 캐시 라인에 매핑하는 것입니다. 예를 들어, 메모리에 4096개의 블록이 있고 이를 위한 64개의 캐시 라인이 있다면, 각 캐시 라인은 언제든 $\frac{4096}{64} = 64$개의 서로 다른 블록 중 하나의 내용을 저장합니다.

![직접 매핑 캐시 (Direct-mapped cache)](../img/cache2.png)

직접 매핑 캐시는 구현하기 쉽고 캐시 라인과 연결된 태그(캐시된 블록의 실제 메모리 위치) 외에는 추가적인 메타 정보를 저장할 필요가 없습니다. 단점은 항목이 너무 빨리 쫓겨날 수 있다는 것입니다. 예를 들어 동일한 캐시 라인으로 매핑되는 두 주소 사이를 오갈 때 전체 캐시 활용도가 낮아지게 됩니다.

이러한 이유로 우리는 직접 매핑 캐시와 완전 연관 캐시의 중간 형태인 *집합 연관 캐시(set-associative cache)*를 사용합니다. 주소 공간을 동일한 그룹으로 나누고, 각 그룹이 개별적으로 작은 완전 연관 캐시 역할을 하도록 하는 방식입니다.

![집합 연관 캐시 (2-way associative)](../img/cache3.png)

*연관성(Associativity)*은 이러한 집합의 크기입니다. 다시 말해, 각 데이터 블록이 매핑될 수 있는 서로 다른 캐시 라인의 수입니다. 연관성이 높을수록 캐시를 더 효율적으로 활용할 수 있지만 비용도 증가합니다.

예를 들어 [제 CPU](https://en.wikichip.org/wiki/amd/ryzen_7/4700u)의 경우 L3 캐시는 16-way 집합 연관 방식이며 단일 코어에서 4MB를 사용할 수 있습니다. 이는 총 $\frac{2^{22}}{2^{6}} = 2^{16}$개의 캐시 라인이 있음을 의미하며, 이들은 $\frac{2^{16}}{16} = 2^{12}$개의 그룹으로 나뉩니다. 각 그룹은 RAM의 $\frac{1}{2^{12}}$ 조각에 대해 자체적인 완전 연관 캐시 역할을 합니다.

명령어 캐시나 TLB와 같이 데이터가 아닌 캐시를 포함하여 대부분의 다른 CPU 캐시도 집합 연관 방식입니다. 예외는 64개 이하의 항목만 수용하는 작은 특수 캐시들로, 이들은 대개 완전 연관 방식입니다.

### 주소 변환 (Address Translation)

마지막으로 한 가지 모호함이 남아 있습니다. 캐시 라인 매핑이 정확히 어떻게 이루어지는가 하는 점입니다.

소프트웨어에서 집합 연관 캐시를 구현한다면 메모리 블록 주소의 해시 함수를 계산한 다음 그 값을 캐시 라인 인덱스로 사용할 것입니다. 하드웨어에서는 이것이 너무 느리기 때문에 그렇게 할 수 없습니다. 예를 들어 L1 캐시의 지연 시간 요구 사항은 4~5사이클인데, [나머지 연산](/hpc/arithmetic/division)만 해도 10~15사이클이 걸리며 더 정교한 작업은 말할 것도 없습니다.

대신 하드웨어는 게으른 접근 방식을 사용합니다. 액세스해야 하는 메모리 주소를 가져와 하위 비트부터 상위 비트까지 세 부분으로 나눕니다:

- *오프셋(offset)* — 64바이트 캐시 라인 내의 워드 인덱스 ($\log_2 64 = 6$ 비트);
- *인덱스(index)* — 캐시 라인 집합의 인덱스 (L3 캐시에 $2^{12}$개의 캐시 라인 그룹이 있으므로 다음 12비트);
- *태그(tag)* — 캐시 라인에 저장된 메모리 블록들을 구분하는 데 사용되는 나머지 메모리 주소.

즉, "중간" 부분이 동일한 모든 메모리 주소는 동일한 집합으로 매핑됩니다.

![64개 항목을 가진 2-way 집합 연관 캐시의 주소 구성](../img/address.png)

이는 캐시 시스템을 더 간단하고 저렴하게 구현할 수 있게 해주지만, 특정한 나쁜 액세스 패턴에 취약하게 만듭니다.

### 병적인 매핑 (Pathological Mappings)

저, 어디까지 이야기했었죠? 아, 맞습니다. 256의 스텝 크기로 반복할 때 끔찍한 속도 저하가 발생하는 이유입니다.

256개의 정수를 뛰어넘을 때 포인터는 항상 $1024 = 2^{10}$만큼 증가하며 마지막 10비트는 동일하게 유지됩니다. 캐시 시스템은 하위 6비트를 오프셋으로 사용하고 다음 12비트를 캐시 라인 인덱스로 사용하므로, 우리는 기본적으로 L3 캐시에서 $2^{12}$개가 아닌 $2^{12 - (10 - 6)} = 2^8$개의 서로 다른 집합만을 사용하게 됩니다. 이는 L3 캐시를 $2^4 = 16$배 축소시키는 효과를 냅니다. 배열이 L3 캐시($N=2^{21}$)에 더 이상 담기지 않게 되고 수십 배 더 느린 RAM으로 넘쳐흐르게 되어 성능이 저하되는 것입니다.

캐시 연관성 효과로 인한 성능 문제는 알고리즘에서 놀라울 정도로 자주 발생합니다. 여러 가지 이유로 프로그래머들이 배열을 인덱싱할 때 2의 거듭제곱을 사용하는 것을 좋아하기 때문입니다:

- 다차원 배열 액세스에서 마지막 차원이 2의 거듭제곱이면 곱셈 대신 이진 시프트만 필요하므로 주소 계산이 더 쉽습니다.
- 2의 거듭제곱으로 나머지 연산을 하기가 더 쉽습니다. 단일 비트 `and`로 가능하기 때문입니다.
- 분할 정복 알고리즘에서 2의 거듭제곱 크기의 문제를 사용하는 것이 편리하고 종종 필수적입니다.
- 2는 가장 작은 정수 지수이므로, 메모리 집약적 알고리즘을 벤치마킹할 때 문제 크기로 증가하는 2의 거듭제곱 시퀀스를 선택하는 것이 인기 있는 선택입니다.
- 또한 더 자연스러운 10의 거듭제곱들도 전이성에 의해 약간 더 낮은 2의 거듭제곱으로 나누어집니다.

이는 특히 고정된 메모리 레이아웃을 사용하는 암시적 자료 구조에 자주 적용됩니다. 예를 들어 크기가 $2^{20}$인 배열에 대한 [이진 탐색](/hpc/data-structures/binary-search)은 쿼리당 약 360ns가 걸리는 반면, 크기가 $(2^{20} + 123)$인 배열에 대한 탐색은 약 300ns가 걸립니다. 배열 크기가 큰 2의 거듭제곱의 배수이면, 처음 십여 번의 반복에서 요청할 가능성이 높은 "가장 뜨거운" 요소들의 인덱스도 큰 2의 거듭제곱으로 나누어떨어지게 되어 동일한 캐시 라인으로 매핑됩니다. 이들은 서로를 쫓아내며 약 20%의 성능 저하를 유발합니다.

다행히 이러한 문제는 심각한 문제라기보다 변칙에 가깝습니다. 해결책은 대개 간단합니다. 2의 거듭제곱으로 반복하는 것을 피하거나, 다차원 배열의 마지막 차원을 약간 다른 크기로 만들거나, 메모리 레이아웃에 "구멍"을 삽입하는 다른 방법을 사용하거나, 배열 인덱스와 데이터가 실제로 저장되는 위치 사이에 무작위적인 일대일 대응(bijection)을 만드는 것입니다.
