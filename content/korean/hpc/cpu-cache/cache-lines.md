---
title: 캐시 라인 (Cache Lines)
weight: 3
---

CPU 캐시 시스템에서 데이터 전송의 기본 단위는 개별 비트나 바이트가 아니라 *캐시 라인(cache lines)*입니다. 대부분의 아키텍처에서 캐시 라인의 크기는 64바이트입니다. 즉, 모든 메모리는 64바이트 블록으로 나뉘어 있으며, 단 하나의 바이트를 요청(읽기 또는 쓰기)할 때마다 원하든 원치 않든 해당 캐시 라인에 속한 나머지 63바이트도 함께 가져오게 됩니다.

이를 증명하기 위해, 우리의 [증가 루프(incrementing loop)](../bandwidth)에 "스텝(step)" 파라미터를 추가해 보겠습니다. 이제 우리는 매 $D$번째 요소만 건드립니다:

```cpp
for (int i = 0; i < N; i += D)
    a[i]++;
```

$D=1$과 $D=16$으로 실행해 보면 흥미로운 점을 관찰할 수 있습니다:

![성능은 증가된 총 요소 수가 아니라 벤치마크 실행에 걸린 총 시간으로 정규화되었습니다](../img/strided.svg)

문제 크기가 커짐에 따라 두 루프의 그래프가 만나는 것을 볼 수 있습니다. 한쪽이 다른 쪽보다 16배 적은 일을 함에도 불구하고 말이죠. 이는 캐시 라인 관점에서 볼 때 두 루프 모두 정확히 동일한 메모리를 가져오고 있으며, 스트라이드 루프가 그중 1/16만 필요로 한다는 사실은 무관하기 때문입니다.

배열이 L1 캐시에 들어갈 때는 스트라이드 버전이 더 빨리 완료됩니다 — 비록 16배는 아니지만 약 2배 정도 빠릅니다. 이는 해야 할 일이 절반으로 줄어들기 때문입니다: 스트라이드 버전은 매 16개 요소마다 단 하나의 `inc DWORD PTR [rdx]` 명령어를 실행하는 반면, 원래 루프는 동일한 16개 요소를 처리하기 위해 두 개의 8요소 [벡터 명령어](/hpc/simd)가 필요했습니다. 두 계산 모두 결과를 다시 쓰는 과정에서 병목 현상이 발생합니다: Zen 2는 사이클당 하나의 워드만 쓸 수 있습니다 — 그것이 하나의 정수로 구성되었든 8개로 구성되었든 상관없이 말이죠.

스텝 파라미터를 8로 바꾸면 그래프가 일치하게 됩니다. 이제 매 16개 요소마다 두 번의 증가와 두 번의 쓰기 작업이 필요하기 때문입니다:

![](../img/strided2.svg)

우리는 이 효과를 사용하여 [지연 시간 벤치마크(latency benchmark)](../latency)에서 캐시 공유를 최소화하고 더 정확하게 측정할 수 있습니다. 순열(permutation)의 인덱스들이 각각 고유한 캐시 라인에 위치하도록 *패딩(pad)*을 추가하면 됩니다:

```c++
struct padded_int {
    int val;
    int padding[15];
};

padded_int q[N / 16];

// 무작위 순열로부터 사이클 생성
// ...

for (int i = 0; i < N / 16; i++)
    k = q[k].val;
```

이제 각 인덱스는 루프를 돌아 다시 요청될 때쯤이면 캐시에서 쫓겨났을 가능성이 훨씬 높아집니다:

![](../img/permutation-padded.svg)

메모리 집약적 알고리즘을 설계하고 분석할 때 중요한 실질적 교훈은 메모리 읽기 및 쓰기의 총 횟수뿐만 아니라 액세스되는 캐시 라인의 수를 세는 것입니다.
