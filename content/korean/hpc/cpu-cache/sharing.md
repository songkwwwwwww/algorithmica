---
title: 메모리 공유 (Memory Sharing)

---

계층 구조의 특정 수준부터 캐시는 서로 다른 코어 간에 *공유(shared)*됩니다. 이는 전체 다이(die) 면적을 줄이고 단일 칩에 더 많은 코어를 추가할 수 있게 해주지만, 단일 실행 스레드에서 사용할 수 있는 유효 캐시 크기와 대역폭을 제한하는 "시끄러운 이웃(noisy neighbor)" 문제를 야기하기도 합니다.

대부분의 CPU에서 마지막 캐시 계층만 공유되며, 항상 균등한 방식은 아닙니다. 제 컴퓨터에는 8개의 물리 코어가 있고 L3 캐시 크기는 8M이지만, 이는 두 개로 나뉘어 있습니다: 4개 코어로 구성된 두 그룹이 각각 고유한 4M L3 캐시 영역에 액세스하며, 전체에 액세스하지는 못합니다.

특정 메모리 영역에 액세스하는 데 걸리는 시간이 코어마다 다른(종종 [의도치 않게](https://randomascii.wordpress.com/2022/01/12/5-5-mm-in-1-25-nanoseconds/)) 훨씬 더 복잡한 토폴로지도 존재합니다. 이러한 아키텍처적 특징을 *불균형 메모리 액세스(non-uniform memory access, NUMA)*라고 하며, 여러 개의 별도 CPU 칩이 설치된 멀티 소켓 시스템에서 나타납니다.

리눅스에서는 `lstopo`를 사용하여 메모리 시스템의 토폴로지를 확인할 수 있습니다:

![lstopo로 생성한 제 Ryzen 7 4700U의 캐시 계층 구조](../img/lstopo.png)

이는 병렬 알고리즘에 중요한 시사점을 줍니다: 멀티 스레드 메모리 액세스의 성능은 어떤 코어가 어떤 실행 스레드를 실행하느냐에 따라 달라집니다. 이를 증명하기 위해 [대역폭 벤치마크](../bandwidth)를 병렬로 실행해 보겠습니다.

### CPU 어피니티 (CPU Affinity)

소스 코드를 수정하여 여러 스레드에서 실행하는 대신, [GNU parallel](https://www.gnu.org/software/parallel/)을 사용하여 여러 개의 동일한 프로세스를 실행할 수 있습니다. 어떤 코어가 이를 실행할지 제어하기 위해 `taskset`으로 *프로세서 어피니티(processor affinity)*를 설정합니다. 다음 명령어는 CPU의 처음 4개 코어에서 실행될 수 있는 4개의 프로세스를 실행합니다:

```bash
parallel taskset -c 0,1,2,3 ./run ::: {0..3}
```

동시에 실행되는 프로세스 수를 변경했을 때의 결과는 다음과 같습니다:

![](../img/parallel.svg)

배열이 각 코어의 개별 캐시인 L2 캐시를 초과하면 성능이 저하되는 것을 볼 수 있습니다. 코어들이 공유 L3 캐시와 RAM을 두고 경쟁하기 시작하기 때문입니다.

우리는 특히 처음 4개의 코어에서 모든 프로세스를 실행하도록 설정했는데, 이들이 통합된 L3 캐시를 공유하기 때문입니다. 만약 일부 프로세스가 다른 절반의 코어에 할당되었다면 L3 캐시에 대한 경합이 덜했을 것입니다. 운영 체제는 이러한 활동을 [모니터링](/hpc/profiling/events)하지 않으며 — 프로세스가 무엇을 하는지는 해당 프로세스의 사적인 일입니다 — 따라서 기본적으로 실행 중에 캐시 어피니티를 신경 쓰지 않고 코어 부하만 고려하여 스레드를 임의로 코어에 할당합니다.

다른 벤치마크를 실행해 보겠습니다. 이번에는 L3 캐시를 공유하지 않는 서로 다른 4코어 그룹에 프로세스를 고정(pinning)합니다:

```bash
parallel taskset -c 0,1 ./run ::: {0..1}  # L3 캐시 공유
parallel taskset -c 0,4 ./run ::: {0..1}  # L3 캐시 공유 안 함
```

L3 캐시와 RAM 대역폭이 두 배로 늘어난 것처럼 성능이 더 좋습니다:

![](../img/affinity.svg)

이러한 문제들은 특히 벤치마킹할 때 까다로우며, 병렬 애플리케이션의 시간을 측정할 때 거대한 노이즈의 원인이 됩니다.

### 대역폭 포화 (Saturating Bandwidth)

첫 번째 그래프의 RAM 섹션을 보면 코어 수가 늘어남에 따라 프로세스당 처리량이 1/2, 1/3, 1/4 등으로 떨어지고 총 대역폭은 일정하게 유지되는 것처럼 보일 수 있습니다. 하지만 이는 아주 사실은 아닙니다: 경합이 손해를 입히기는 하지만, 단일 CPU 코어는 대개 RAM 대역폭 전체를 포화시키지 못하기 때문입니다.

더 세밀하게 그래프를 그려보면, 비록 비례하지는 않더라도 코어 수에 따라 총 대역폭이 실제로 증가하며 결국 이론적 최대치인 ~42.4 GB/s에 도달하는 것을 볼 수 있습니다:

![](../img/parallel-bandwidth.svg)

여기서도 프로세서 어피니티를 지정했습니다: $k$-스레드 실행은 처음 $k$개의 코어를 사용합니다. 이것이 4코어에서 5코어로 전환될 때 성능이 급격히 증가하는 이유입니다: 요청이 별도의 L3 캐시를 거쳐가기 때문에 더 많은 RAM 대역폭을 확보할 수 있습니다.

일반적으로 최대 대역폭을 달성하려면 애플리케이션의 스레드를 항상 대칭적으로 분할해야 합니다.
