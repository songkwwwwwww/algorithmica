title: 메모리 대역폭 (Memory Bandwidth)

---

CPU 레지스터와 RAM 사이의 데이터 경로에는 자주 사용되는 데이터에 대한 액세스 속도를 높이기 위해 *캐시* 계층 구조가 존재합니다. 프로세서에 가까운 계층일수록 더 빠르지만 크기는 더 작습니다. 여기서 "빠르다"라는 말은 서로 밀접하게 관련되어 있지만 별개인 두 가지 타이밍에 적용됩니다:

- 읽기 또는 쓰기가 시작된 시점과 데이터가 도착하는 시점 사이의 지연 (*지연 시간, latency*).
- 단위 시간당 처리할 수 있는 메모리 연산의 수 (*대역폭, bandwidth*).

많은 알고리즘에서 메모리 대역폭은 캐시 시스템의 가장 중요한 특성입니다. 동시에 측정하기 가장 쉬운 특성이기도 하므로, 대역폭부터 측정해 보겠습니다.

실험을 위해 배열을 만들고 $K$번 반복하며 그 값을 증가시키는 코드를 작성합니다:

```cpp
int a[N];

for (int t = 0; t < K; t++)
    for (int i = 0; i < N; i++)
        a[i]++;
```

$N$을 변경하고 총 액세스되는 배열 셀 수가 거의 일정하도록 $K$를 조정하여 총 시간을 "초당 연산 횟수"로 표현하면 다음과 같은 그래프를 얻게 됩니다:

![점선 수직선은 캐시 계층별 크기입니다](../img/inc.svg)

이 그래프에서 캐시 크기를 명확히 확인할 수 있습니다:

- 전체 배열이 가장 낮은 캐시 계층에 들어갈 때, 프로그램은 L1 캐시 대역폭보다는 CPU에 의해 병목 현상이 발생합니다. 배열이 커질수록 루프의 첫 번째 반복들과 관련된 오버헤드가 작아지고, 성능은 이론적 최대치인 16 GFLOPS에 가까워집니다.
- 하지만 그 이후 성능이 떨어집니다. 먼저 L1 캐시를 초과할 때 12-13 GFLOPS로 떨어지고, L3 캐시에 더 이상 담기지 않게 되면 점차 약 2 GFLOPS까지 떨어집니다.

이러한 상황은 많은 가벼운 루프에서 전형적으로 나타납니다.

### 주파수 스케일링 (Frequency Scaling)

모든 CPU 캐시 계층은 프로세서와 동일한 마이크로칩에 위치하므로 대역폭, 지연 시간 및 기타 모든 특성이 클록 주파수에 따라 달라집니다. 반면 RAM은 독자적인 고정 클록으로 작동하므로 그 특성이 일정하게 유지됩니다. 터보 부스트를 켠 상태에서 동일한 벤치마크를 다시 실행하여 이를 관찰할 수 있습니다:

![](../img/boost.svg)

이러한 세부 사항은 알고리즘 구현을 비교할 때 중요하게 작용합니다. 작업 데이터셋이 캐시에 들어갈 때는 RAM이 클록 속도의 영향을 받지 않기 때문에(다른 모든 것은 영향을 받지만), 두 구현의 상대적 성능이 CPU 클록 속도에 따라 달라질 수 있습니다.

이러한 이유로 클록 속도를 고정하는 것이 [권장되며](/hpc/profiling/noise), 터보 부스트는 충분히 안정적이지 않으므로 이 책의 대부분의 벤치마크는 평범한 2GHz에서 실행합니다.

### 방향성 액세스 (Directional Access)

이 증가 루프는 실행 중에 읽기와 쓰기를 모두 수행해야 합니다. 각 반복마다 값을 가져와서 증가시킨 다음 다시 써야 하기 때문입니다. 많은 애플리케이션에서는 이 중 하나만 필요하므로 단방향 대역폭을 측정해 보겠습니다.

배열의 합계를 계산하는 것은 메모리 읽기만 필요합니다:

```c++
for (int i = 0; i < N; i++)
    s += a[i];
```

그리고 배열을 0으로 만드는 것(또는 다른 상수로 채우는 것)은 메모리 쓰기만 필요합니다:

```c++
for (int i = 0; i < N; i++)
    a[i] = 0;
```

두 루프 모두 컴파일러에 의해 트리비얼하게 [벡터화(vectorized)](/hpc/simd)되며, 두 번째 루프는 실제로는 `memset`으로 대체되므로 여기서도 CPU가 병목 현상이 되지는 않습니다 (배열이 L1 캐시에 들어가는 경우 제외).

![](../img/directional.svg)

단방향 및 양방향 메모리 액세스의 성능이 다르게 나타나는 이유는 이들이 캐시와 메모리 버스 및 기타 CPU 시설을 공유하기 때문입니다. RAM의 경우, 순수 읽기 시나리오와 동시 읽기 및 쓰기 시나리오 사이에 성능 차이가 두 배나 발생합니다. 메모리 컨트롤러가 단방향 메모리 버스에서 모드를 전환해야 하므로 대역폭이 절반으로 줄어들기 때문입니다. L2 캐시의 경우 성능 저하가 덜 심각한데, 여기서 병목 현상은 캐시 버스가 아니기 때문에 증가 루프가 약 15% 정도만 손해를 봅니다.

그래프에서 흥미로운 변칙이 하나 있는데, 배열이 L3 캐시와 RAM에 도달할 때 쓰기 전용 루프가 읽기 및 쓰기 루프와 동일한 성능을 보인다는 점입니다. 이는 CPU가 읽기든 쓰기든 모든 액세스 시 데이터를 최고 수준의 캐시로 이동시키기 때문입니다. 이는 많은 사용 사례에서 곧 해당 데이터가 필요할 것이라는 점에서 대개 좋은 최적화입니다. 데이터를 읽을 때는 데이터가 어차피 캐시 계층 구조를 거쳐 이동하므로 문제가 되지 않지만, 쓸 때는 쓰기 직후에 또 다른 암시적인 읽기가 파견되어 버스 대역폭을 두 배로 사용하게 됩니다.

### 캐시 우회 (Bypassing the Cache)

*비임시(non-temporal)* 메모리 액세스를 사용하면 방금 쓴 데이터를 CPU가 프리페치(prefetch)하는 것을 방지할 수 있습니다. 이를 위해 컴파일러 벡터화에 의존하지 않고 제로화 루프를 더 직접적으로 재구현해야 합니다.

몇 가지 특수한 경우를 제외하고, `memset`과 자동 벡터화된 할당 루프가 내부적으로 수행하는 작업은 단순히 [SIMD 명령어](/hpc/simd)를 사용하여 32바이트 데이터 블록을 [이동시키는 것](/hpc/simd/moving)입니다:

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_store_si256((__m256i*) &a[i], zeros);
```

우리는 일반적인 벡터 저장 인트린직을 *비임시(non-temporal)* 인트린직으로 대체할 수 있습니다:

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_stream_si256((__m256i*) &a[i], zeros);
```

비임시 메모리 읽기 또는 쓰기는 방금 액세스한 데이터가 나중에 필요하지 않을 것임을 CPU에 알리는 방법이며, 따라서 쓰기 후에 데이터를 다시 읽을 필요가 없습니다.

![](../img/non-temporal.svg)

한편으로, 배열이 캐시에 담길 만큼 충분히 작고 나중에 실제로 액세스한다면 이는 부정적인 영향을 미칩니다. 데이터를 RAM에서 전부 읽어와야 하기 때문입니다 (이 경우에는 로컬로 캐시된 버전을 사용하는 대신 RAM에 *써야* 합니다). 다른 한편으로, 이는 리드백(read-backs)을 방지하고 메모리 버스를 더 효율적으로 사용할 수 있게 해줍니다.

사실 RAM의 경우 성능 향상은 2배 이상이며 읽기 전용 벤치마크보다도 빠릅니다. 이는 다음과 같은 이유 때문입니다:

- 메모리 컨트롤러가 버스를 읽기 및 쓰기 모드 사이에서 전환할 필요가 없습니다.
- 명령어 시퀀스가 단순해져 더 많은 펜딩(pending) 메모리 명령어가 가능해집니다.
- 가장 중요하게는, 메모리 컨트롤러가 비임시 쓰기 요청을 단순히 "쏘고 잊어버릴(fire and forget)" 수 있습니다. 반면 읽기의 경우 데이터가 도착했을 때 무엇을 할지 기억해야 합니다 (네트워킹 소프트웨어의 연결 핸들과 유사함).

이론적으로 두 요청 모두 동일한 대역폭을 사용해야 합니다. 읽기 요청은 주소를 보내고 데이터를 받고, 비임시 쓰기 요청은 주소를 데이터와 *함께* 보내고 아무것도 받지 않습니다. 방향을 고려하지 않으면 동일한 데이터를 전송하지만, 읽기 사이클은 데이터를 가져오기를 기다려야 하므로 더 길어집니다. 메모리 시스템이 처리할 수 있는 동시 요청 수에 [실제적인 제한](../mlp)이 있기 때문에, 읽기/쓰기 사이클 지연 시간의 차이는 대역폭의 차이로 이어집니다.

또한 이러한 이유로 단일 CPU 코어는 대개 [메모리 대역폭을 완전히 포화시키지 못합니다](../sharing).

동일한 기술이 `memcpy`에도 일반화됩니다. `memcpy` 역시 SIMD 로드/스토어 명령어로 32바이트 블록을 이동시킬 뿐이며, 마찬가지로 비임시로 만들 수 있어 큰 배열에 대해 처리량을 두 배로 늘릴 수 있습니다. 또한 캐시를 오염시키지 않고 *읽고* 싶을 때를 위한 비임시 로드 명령어(`_mm256_stream_load_si256`)도 있습니다 (예를 들어 `memcpy` 후에 원본 배열은 필요 없지만 호출 전 액세스했던 데이터가 필요한 경우).
