동시에 가져와야 하는 데이터들을 함께 그룹화하는 것이 종종 유익합니다. 가급적이면 동일한 캐시 라인에, 그것이 불가능하다면 인접한 캐시 라인에 두는 것이 좋습니다. 이는 메모리 액세스의 [공간 지역성(spatial locality)](/hpc/external-memory/locality)을 향상시켜 메모리 집약적(memory-bound) 알고리즘의 성능에 긍정적인 영향을 미칩니다.

이렇게 하는 것의 잠재적인 효과를 보여주기 위해, 다음 포인터를 하나가 아닌 가변적인 수의 필드($D$)를 사용하여 계산하도록 [포인터 추적(pointer chasing)](../latency) 벤치마크를 수정해 보겠습니다.

### 실험 (Experiment)

첫 번째 접근 방식은 이러한 필드들을 2차원 배열의 행으로서 함께 배치하는 것입니다. 이 변형을 *구조체 배열(array of structures, AoS)*이라고 부르겠습니다:

```c++
const int M = N / D; // 메모리 액세스 횟수
int p[M], q[M][D];

iota(p, p + M, 0);
random_shuffle(p, p + M);

int k = p[M - 1];

for (int i = 0; i < M; i++)
    q[k][0] = p[i];

    for (int j = 1; j < D; j++)
        q[i][0] ^= (q[j][i] = rand());

    k = q[k][0];
}

for (int i = 0; i < M; i++) {
    int x = 0;
    for (int j = 0; j < D; j++)
        x ^= q[k][j];
    k = x;
}
```

그리고 두 번째 접근 방식에서는 필드들을 별도로 배치합니다. 이를 수행하는 가장 간단한 방법은 2차원 배열 `q`를 전치(transpose)하고 이후의 모든 액세스에서 인덱스를 바꾸는 것입니다.

```c++
int q[D][M];
//    ^--^
```

유사하게, 이 변형을 *배열 구조체(structure of arrays, SoA)*라고 부릅니다. 분명히 $D$가 클수록 이 방식은 훨씬 더 나쁜 성능을 보입니다.

![](../img/aos-soa.svg)

두 변형의 성능은 모두 $D$에 따라 선형적으로 증가하지만, AoS는 데이터가 순차적으로 저장되어 있기 때문에 총 캐시 라인을 최대 16배 적게 가져와야 합니다. $D=64$인 경우에도 다른 63개의 값을 처리하는 데 걸리는 추가 시간은 첫 번째 데이터를 가져오는 지연 시간보다 짧습니다.

또한 2의 거듭제곱 지점에서 스파이크가 발생하는 것을 볼 수 있습니다. AoS는 SIMD를 사용하여 [수평 xor-합(horizontal xor-sum)](/hpc/simd/reduction)을 더 빨리 계산할 수 있기 때문에 약간 더 나은 성능을 보입니다. 반면 SoA는 훨씬 더 나쁜 성능을 보이는데, 이는 $D$ 때문이 아니라 두 번째 차원의 크기인 $\lfloor N / D \rfloor$가 큰 2의 거듭제곱이기 때문입니다. 이로 인해 매우 복잡한 [캐시 연관성(cache associativity)](../associativity) 효과가 발생합니다.

### 임시 저장소 경합 (Temporary Storage Contention)

처음에는 $N=2^{23}$이고 배열이 L3 캐시에 담기에는 너무 크기 때문에 캐시 문제가 없을 것처럼 보입니다. 뉘앙스는 서로 다른 메모리 위치의 여러 요소를 병렬로 처리하려면 여전히 이를 임시로 저장할 공간이 필요하다는 점입니다. 레지스터는 수가 충분하지 않아 단순히 레지스터를 사용할 수 없으므로, 비록 1마이크로초 후에는 필요하지 않게 되더라도 캐시에 저장되어야 합니다.

따라서 `N / D`가 큰 2의 거듭제곱이고 첫 번째 인덱스를 따라 배열 `q[D][N / D]`를 반복할 때, 임시로 필요한 일부 메모리 주소들이 동일한 캐시 라인으로 매핑됩니다. 그곳에 충분한 공간이 없으므로 많은 주소들이 메모리 계층 구조의 상위 레이어에서 다시 읽어와야 합니다.

여기에 또 다른 수수께끼가 있습니다. 만약 [거대 페이지(huge pages)](../paging)를 활성화하면 예상대로 대부분의 $D$ 값에 대해 총 지연 시간이 10-15% 낮아지지만, $D=64$일 때는 상황이 10배나 더 나빠집니다.

![로그 스케일에 유의하십시오](../img/soa-hugepages.svg)

메모리 컨트롤러를 설계하는 엔지니어들조차 여기서 무슨 일이 일어나고 있는지 즉석에서 설명하기는 어려울 것입니다.

요약하자면, 각 코어에 개별적으로 할당된 L1/L2 캐시와 달리 L3 캐시는 캐시를 공유하는 서로 다른 코어 간의 동기화를 위해 가상 주소 대신 *물리(physical)* 메모리 주소를 사용해야 하기 때문에 차이가 발생합니다.

4K 메모리 페이지를 사용할 때는 가상 주소가 물리 메모리상에 다소 임의로 분산되는데, 이는 캐시 연관성 문제를 덜 심각하게 만듭니다. 물리 주소들은 4K 바이트를 모듈로 하여 동일한 나머지를 갖게 되며, 가상 주소처럼 `N / D`를 모듈로 하지 않기 때문입니다. 우리가 특별히 거대 페이지를 요구하면 이 최대 정렬 제한이 2M로 증가하고 캐시 라인은 훨씬 더 많은 경합을 겪게 됩니다.

이것은 거대 페이지를 활성화했을 때 성능이 저하되는, 심지어 10배나 저하되는 제가 아는 유일한 예입니다.

### 패딩된 AoS (Padded AoS)

동일한 수의 캐시 라인을 가져오는 한 그 데이터가 어디에 위치하든 상관없겠죠? 이를 테스트해 보기 위해 AoS 코드에서 [패딩된 정수(padded integers)](../cache-lines)로 전환해 보겠습니다.

```c++
struct padded_int {
    int val;
    int padding[15];
};

const int M = N / D / 16;
padded_int q[M][D];
```

그 외에는 여전히 $D$개의 패딩된 정수의 xor-합을 계산하고 있습니다. 정확히 $D$개의 캐시 라인을 가져오지만 이번에는 순차적으로 가져옵니다. 실행 시간은 SoA와 다르지 않아야 하지만 실제로는 그렇지 않습니다.

![](../img/aos-soa-padded.svg)

$D=63$일 때 실행 시간은 약 ⅓ 정도 낮아지지만, 이는 L3 캐시를 초과하는 배열에만 적용됩니다. $D$를 고정하고 $N$을 변경해 보면, 패딩된 버전이 작은 배열에서는 무작위 [캐시 공유(cache sharing)](../cache-lines) 기회가 적어 약간 더 나쁜 성능을 보이는 것을 볼 수 있습니다.

![](../img/aos-soa-padded-n.svg)

작은 배열 크기에서는 성능이 영향을 받지 않으므로, 이는 분명히 RAM의 작동 방식과 관련이 있습니다.

### RAM 특유의 타이밍 (RAM-Specific Timings)

성능 분석 관점에서 RAM의 모든 데이터는 물리적으로 행(rows)과 열(columns)로 나뉜 작은 커패시터 셀들의 2차원 배열에 저장됩니다. 어떤 셀이든 읽거나 쓰려면 한 가지, 두 가지 또는 세 가지 작업을 수행해야 합니다.

1. *행 버퍼(row buffer)*에서 행의 내용을 읽습니다. 이 과정에서 커패시터가 일시적으로 방전됩니다.
2. 이 버퍼에서 특정 셀을 읽거나 씁니다.
3. 데이터가 보존되고 행 버퍼가 다른 메모리 액세스에 사용될 수 있도록 행 버퍼의 내용을 다시 커패시터에 씁니다.

여기 핵심이 있습니다. 동일한 행에 해당하는 두 메모리 액세스 사이에서 1단계와 3단계를 수행할 필요가 없습니다. 행 버퍼를 임시 캐시로 사용할 수 있기 때문입니다. 이 세 가지 작업은 대략 동일한 시간이 걸리므로, 이 최적화를 통해 일련의 행-로컬 액세스는 분산된 액세스 패턴에 비해 3배 빠르게 실행됩니다.

![](../img/ram.png)

행의 크기는 하드웨어에 따라 다르지만 보통 1024바이트에서 8192바이트 사이입니다. 따라서 패딩된 AoS 벤치마크가 각 요소를 별도의 캐시 라인에 배치하더라도 동일한 RAM 행에 있을 가능성이 매우 높으며, 전체 읽기 시퀀스는 첫 번째 메모리 액세스 지연 시간에 더해 대략 ⅓의 시간 내에 실행됩니다.
