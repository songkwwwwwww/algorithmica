메모리가 64바이트 [캐시 라인](../cache-lines)으로 분할되어 있다는 사실은 캐시 라인 경계를 넘나드는 데이터 워드를 처리하는 것을 어렵게 만듭니다. 32비트 정수와 같은 기본 타입을 가져와야 할 때, 해당 데이터가 단일 캐시 라인에 위치하기를 원하게 됩니다. 두 개의 캐시 라인을 가져오는 것은 더 많은 메모리 대역폭을 필요로 할 뿐만 아니라, 하드웨어에서 결과를 결합하는 데 귀중한 트랜지스터 공간이 필요하기 때문입니다.

이러한 측면은 알고리즘 설계와 컴파일러가 데이터 구조의 메모리 레이아웃을 선택하는 방식에 큰 영향을 미칩니다.

### 정렬된 할당 (Aligned Allocation)

기본적으로 기본 타입의 배열을 할당할 때, 모든 요소의 주소는 해당 타입 크기의 배수임이 보장되며, 이는 각 요소가 단일 캐시 라인에만 걸쳐 있도록 보장합니다. 예를 들어, `int` 배열의 첫 번째 요소와 모든 다른 요소의 주소는 4바이트(`sizeof int`)의 배수임이 보장됩니다.

때로는 이 최소 정렬 단위를 더 높게 보장해야 할 때가 있습니다. 예를 들어, 많은 [SIMD](/hpc/simd) 애플리케이션은 32바이트 블록 단위로 데이터를 읽고 쓰는데, 이 32바이트가 동일한 캐시 라인에 속하는 것이 [성능에 결정적](/hpc/simd/moving)입니다. 이러한 경우 정적 배열 변수를 정의할 때 `alignas` 지정자를 사용할 수 있습니다.

```c++
alignas(32) float a[n];
```

동적으로 메모리 정렬된 배열을 할당하려면 `std::aligned_alloc`을 사용할 수 있습니다. 이 함수는 정렬 값과 배열의 바이트 크기를 인자로 받아 할당된 메모리에 대한 포인터를 반환합니다 (`new` 연산자와 유사하게 작동합니다):

```c++
void *a = std::aligned_alloc(32, 4 * n);
```

캐시 라인보다 [더 큰 크기](../paging)로 메모리를 정렬할 수도 있습니다. 유일한 제한 사항은 크기 파라미터가 정렬 값의 정수 배수여야 한다는 것입니다.

`struct`를 정의할 때도 `alignas` 지정자를 사용할 수 있습니다.

```c++
struct alignas(64) Data {
    // ...
};
```

`Data` 인스턴스가 할당될 때마다 항상 캐시 라인의 시작 부분에 위치하게 됩니다. 단점은 구조체의 유효 크기가 64바이트의 가장 가까운 배수로 올림된다는 점입니다. 이는 예를 들어 `Data` 배열을 할당할 때 첫 번째 요소뿐만 아니라 모든 요소가 적절히 정렬되도록 하기 위해 필요합니다.

### 구조체 정렬 (Structure Alignment)

구조체와 같이 서로 다른 타입의 요소 그룹을 할당해야 할 때 이 문제는 더 복잡해집니다. 각 멤버가 단일 캐시 라인 내에 있도록 `struct` 멤버들을 재배치하는 테트리스를 하는 대신(구조체 자체가 캐시 라인의 시작점에 놓인다는 보장이 없으므로 항상 가능한 것은 아닙니다), 대부분의 C/C++ 컴파일러도 메모리 정렬 메커니즘에 의존합니다.

구조체 정렬은 마찬가지로 모든 멤버 기본 타입(`char`, `int`, `float*` 등)의 주소가 해당 타입 크기의 배수가 되도록 보장하며, 이는 자동으로 각 멤버가 하나의 캐시 라인에만 걸쳐 있도록 보장합니다. 이는 다음과 같은 방식으로 달성됩니다:

- 필요한 경우, 다음 멤버의 정렬 요구 사항을 충족하기 위해 각 구조체 멤버 뒤에 가변적인 수의 빈 바이트를 추가하는 *패딩(padding)*을 수행합니다.
- 구조체 자체의 정렬 요구 사항을 멤버 타입들의 정렬 요구 사항 중 최댓값으로 설정합니다. 이를 통해 해당 구조체 타입의 배열이 할당되거나 다른 구조체의 멤버 타입으로 사용될 때 모든 기본 타입의 정렬 요구 사항이 충족되도록 합니다.

더 나은 이해를 위해 다음 예제를 살펴보십시오:

```cpp
struct Data {
    char a;
    short b;
    int c;
    char d;
};
```

조밀하게 저장될 경우 이 구조체는 인스턴스당 총 $1 + 2 + 4 + 1 = 8$바이트가 필요하지만, 전체 구조체가 4바이트(가장 큰 멤버인 `int`) 정렬을 갖는다고 가정하더라도 `a`만 괜찮을 뿐, `b`, `c`, `d`는 크기 정렬이 되지 않아 잠재적으로 캐시 라인 경계를 넘게 됩니다.

이를 해결하기 위해 컴파일러는 각 다음 멤버가 올바른 최소 정렬을 갖도록 이름 없는 멤버들을 삽입합니다:

```cpp
struct Data {
    char a;    // 1 바이트
    char x[1]; // 다음 "short"가 2바이트 경계에 정렬되도록 하기 위한 1바이트 패딩
    short b;   // 2 바이트 
    int c;     // 4 바이트 (가장 큰 멤버, 전체 구조체의 정렬을 결정함)
    char d;    // 1 바이트
    char y[3]; // 구조체의 총 크기를 12바이트(4로 나누어 떨어짐)로 만들기 위한 3바이트 패딩
};

// sizeof(Data) = 12
// alignof(Data) = alignof(int) = sizeof(int) = 4
```

이는 잠재적으로 공간을 낭비하지만 많은 CPU 사이클을 절약합니다. 이러한 절충은 대개 유익하므로 대부분의 컴파일러에서 구조체 정렬은 기본적으로 활성화되어 있습니다.

### 멤버 순서 최적화 (Optimizing Member Order)

패딩은 아직 정렬되지 않은 멤버 앞이나 구조체의 끝에만 삽입됩니다. 구조체 내 멤버들의 순서를 변경함으로써 필요한 패딩 바이트 수와 구조체의 총 크기를 줄일 수 있습니다.

이전 예제에서 구조체 멤버의 순서를 다음과 같이 바꿀 수 있습니다:

```c++
struct Data {
    int c;
    short b;
    char a;
    char d;
};
```

이제 각 멤버는 패딩 없이 정렬되며, 구조체 크기는 단 8바이트가 됩니다. 구조체의 크기와 그에 따른 성능이 멤버 정의 순서에 따라 달라진다는 것이 이상해 보일 수 있지만, 이는 바이너리 호환성을 위해 필요합니다.

어림잡아 계산하자면, 데이터 타입을 큰 것부터 작은 것 순으로 배치하십시오. 이 탐욕 알고리즘(greedy algorithm)은 [10바이트](/hpc/arithmetic/ieee-754#float-formats) `long double`[^extended]과 같이 2의 거듭제곱이 아닌 특이한 크기의 타입이 있지 않는 한 반드시 작동합니다.

[^extended]: 80비트 `long double`은 *최소* 10바이트를 차지하지만, 정확한 포맷은 컴파일러에 달려 있습니다. 예를 들어, 정렬 문제를 최소화하기 위해 12 또는 16바이트로 패딩할 수 있습니다 (64비트 GCC와 Clang은 기본적으로 16바이트를 사용하며, `-mlong-double-64/80/128` 또는 `-m96/128bit-long-double` [옵션](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html) 중 하나를 지정하여 이를 변경할 수 있습니다).

### 구조체 패킹 (Structure Packing)

자신이 무엇을 하고 있는지 잘 알고 있다면, 구조체 패딩을 비활성화하고 데이터를 가능한 한 조밀하게 팩킹(pack)할 수 있습니다.

이러한 기능은 아직 C나 C++ 표준의 일부가 아니므로 컴파일러에 명시적으로 요청해야 합니다. GCC와 Clang에서는 `packed` 속성을 사용하여 수행합니다.

```cpp
struct __attribute__ ((packed)) Data {
    long long a;
    bool b;
};
```

이렇게 하면 `Data` 인스턴스는 정렬에 필요한 16바이트 대신 단 9바이트만 차지하게 되지만, 요소를 읽기 위해 두 개의 캐시 라인을 가져와야 할 수도 있다는 비용이 발생합니다.

### 비트 필드 (Bit fields)

패킹과 함께 *비트 필드(bit fields)*를 사용할 수도 있습니다. 이를 통해 멤버의 크기를 비트 단위로 명시적으로 고정할 수 있습니다:

```cpp
struct __attribute__ ((packed)) Data {
    char a;     // 1 바이트
    int b : 24; // 3 바이트
};
```

이 구조체는 패킹되었을 때 4바이트를 차지하며, 패딩되었을 때는 8바이트를 차지합니다. 멤버의 비트 수가 반드시 8의 배수일 필요는 없으며, 전체 구조체 크기도 마찬가지입니다. `Data` 배열에서 바이트 단위로 떨어지지 않는 경우 인접한 요소들이 "병합"됩니다. 또한 기본 타입보다 큰 너비를 설정할 수도 있는데, 이는 패딩 역할을 합니다 (비록 그 과정에서 경고가 발생하긴 하지만요).

이 기능은 널리 사용되지는 않는데, CPU에 3바이트 산술 연산 등이 없어서 로딩 중에 비효율적인 바이트 단위 변환을 수행해야 하기 때문입니다:

```cpp
int load(char *p) {
    char x = p[0], y = p[1], z = p[2];
    return (x << 16) + (y << 8) + z;
}
```

바이트 단위로 떨어지지 않는 경우 오버헤드는 더욱 커집니다. 시프트와 and-마스크로 처리해야 하기 때문입니다.

이 절차는 4바이트 `int`를 로드한 다음 마스크를 사용하여 상위 비트를 버리는 방식으로 최적화할 수 있습니다.

```cpp
int load(int *p) {
    int x = *p;
    return x & ((1<<24) - 1);
}
```

컴파일러는 일반적으로 이를 수행하지 않는데, 기술적으로 합법적이지 않기 때문입니다. 그 4번째 바이트가 소유하지 않은 메모리 페이지에 있을 수 있으며, 이 경우 운영 체제는 해당 바이트를 로드한 직후 바로 버릴 것이라 하더라도 로드를 허용하지 않을 것입니다.
