메모리 요청은 시간상으로 중첩될 수 있습니다. 하나의 읽기 요청이 완료되기를 기다리는 동안 다른 요청들을 보낼 수 있으며, 이들은 동시에 실행됩니다. 이것이 [선형 반복(linear iteration)](../bandwidth)이 [포인터 점프(pointer jumping)](../latency)보다 훨씬 빠른 주된 이유입니다. CPU가 다음에 가져와야 할 메모리 위치를 알고 메모리 요청을 훨씬 미리 보내기 때문입니다.

동시에 수행 가능한 메모리 연산의 수는 많지만 제한되어 있으며, 메모리 유형마다 다릅니다. 알고리즘, 특히 자료 구조를 설계할 때 이 숫자를 알고 싶을 수 있습니다. 계산이 달성할 수 있는 병렬성의 양을 제한하기 때문입니다.

특정 메모리 유형에 대한 이 한계를 이론적으로 찾으려면, 지연 시간(캐시 라인을 가져오는 시간)에 대역폭(초당 가져오는 캐시 라인 수)을 곱하면 됩니다. 이는 현재 진행 중인 평균 메모리 연산 수를 제공합니다:

![](../img/latency-bandwidth.svg)

L1/L2 캐시의 지연 시간은 작아서 펜딩(pending) 요청의 긴 파이프라인이 필요하지 않지만, 더 큰 메모리 유형은 최대 25~40개의 동시 읽기 연산을 감당할 수 있습니다.

### 직접 실험 (Direct Experiment)

단 하나가 아니라 $D$개의 개별 사이클을 병렬로 돌도록 포인터 추적 벤치마크를 수정하여 사용 가능한 메모리 병렬성을 더 직접적으로 측정해 봅시다:

```c++
const int M = N / D;
int p[M], q[D][M];

for (int d = 0; d < D; d++) {
    iota(p, p + M, 0);
    random_shuffle(p, p + M);
    k[d] = p[M - 1];
    for (int i = 0; i < M; i++)
        k[d] = q[d][k[d]] = p[i];
}

for (int i = 0; i < M; i++)
    for (int d = 0; d < D; d++)
        k[d] = q[d][k[d]];
```

사이클 길이의 합을 몇 가지 크기로 고정하고 다양한 $D$를 시도해 보면 약간씩 다른 결과를 얻게 됩니다:

![](../img/permutation-mlp.svg)

L2 캐시 실행은 예측대로 약 6개의 동시 연산으로 제한되지만, 더 큰 메모리 유형들은 모두 13에서 17 사이에서 최대치에 도달합니다. 논리 레지스터에 대한 충돌이 발생하기 때문에 더 많은 메모리 레인을 활용할 수 없습니다. 레인 수가 레지스터 수보다 적을 때는 레인당 단 하나의 읽기 명령어를 실행할 수 있습니다:

```nasm
dec     edx
movsx   rdi, DWORD PTR q[0+rdi*4]
movsx   rsi, DWORD PTR q[1048576+rsi*4]
movsx   rcx, DWORD PTR q[2097152+rcx*4]
movsx   rax, DWORD PTR q[3145728+rax*4]
jne     .L9
```

하지만 약 15개를 넘어가면 임시 메모리 저장소를 사용해야 합니다:

```nasm
mov     edx, DWORD PTR q[0+rdx*4]
mov     DWORD PTR [rbp-128+rax*4], edx
```

항상 가능한 최대 수준의 메모리 병렬성에 도달하는 것은 아니지만, 대부분의 애플리케이션에서 수십 개의 동시 요청이면 충분하고도 남습니다.
