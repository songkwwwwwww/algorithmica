[지연 시간 벤치마크](../latency)에서는 단순함을 위해 실제 포인터를 사용하지 않고 베이스 주소에 대한 정수 인덱스를 사용했습니다:

```c++
for (int i = 0; i < N; i++)
    k = q[k];
```

x86의 [메모리 주소 지정 연산자](/hpc/architecture/assembly#addressing-modes)는 주소 계산과 융합되어 있으므로, `k = q[k]` 라인은 내부적으로 4를 곱하고 더하는 동작까지 수행하는 단일 명령어로 축약됩니다:

```nasm
mov rax, DWORD PTR q[0+rax*4]
```

비록 완전히 융합되어 있더라도, 이러한 추가적인 계산은 메모리 연산에 약간의 지연을 더합니다. L1 페치의 지연 시간은 4 또는 5 사이클입니다 — 후자는 복잡한 주소 계산이 필요한 경우입니다. 이러한 이유로 순열 벤치마크는 점프당 3ns 또는 6 사이클을 측정합니다: 읽기 및 주소 계산에 4+1 사이클, 그리고 결과를 올바른 레지스터로 이동시키는 데 1 사이클이 더 소요됩니다.

### 포인터 (Pointers)

"가짜 포인터"인 인덱스를 실제 포인터로 교체하면 벤치마크를 약간 더 빠르게 실행할 수 있습니다.

"포인터의 포인터의 포인터..." 구문을 작동시키는 데 몇 가지 문법적 문제가 있으므로, 대신 자체 타입에 대한 포인터를 감싸는 구조체를 정의하겠습니다 — 대부분의 포인터 추적 방식이 실제로 이렇게 작동하기도 합니다:

```cpp
struct node { node* ptr; };
```

이제 배열을 무작위 포인터로 채우고 이를 추적해 보겠습니다:

```cpp
node* k = q + p[N - 1];

for (int i = 0; i < N; i++)
    k = k->ptr = q + p[i];

for (int i = 0; i < N; i++)
    k = k->ptr;
```

이 코드는 이제 L1 캐시에 들어가는 배열에 대해 2ns / 4 사이클 만에 실행됩니다. 왜 4+1=5가 아닐까요? Zen 2에는 주소로만 액세스되는 데이터의 제로 지연 재사용을 허용하는 [흥미로운 기능](https://www.agner.org/forum/viewtopic.php?t=41)이 있어 여기서 "이동(move)"이 투명하게 처리되어 총 2 사이클을 절약하기 때문입니다.

불행히도 64비트 시스템에서는 포인터 크기가 두 배가 되어 32비트 인덱스를 사용할 때보다 배열이 훨씬 빨리 캐시에서 넘쳐흐르게 된다는 문제가 있습니다. 지연 시간 대 크기 그래프는 예상대로 왼쪽으로 2의 1거듭제곱만큼 이동한 것처럼 보입니다:

![](../img/permutation-p64.svg)

이 문제는 32비트 모드로 전환함으로써 완화될 수 있습니다:

![](../img/permutation-p32.svg)

이번 세기에 만들어진 컴퓨터에서 이를 실행하려면 32비트 라이브러리를 설치하는 등의 [번거로움](https://askubuntu.com/questions/91909/trouble-compiling-a-32-bit-binary-on-a-64-bit-machine)을 감수해야 하지만, 64비트 소프트웨어와 상호 작용하거나 4G 이상의 RAM에 액세스해야 하는 경우가 아니라면 다른 문제는 없을 것입니다.

### 비트 필드 (Bit Fields)

문제 크기가 커질수록 성능이 CPU보다는 메모리에 의해 병목 현상이 발생한다는 사실을 이용해 더 기이한 시도를 해볼 수 있습니다: 인덱스를 저장하는 데 4바이트 미만을 사용하는 것입니다. 이는 [비트 필드](../alignment#bit-fields)로 가능합니다:

```cpp
struct __attribute__ ((packed)) node { int idx : 24; };
```

비트 필드를 위한 구조체를 정의하는 것 외에 다른 작업은 필요 없습니다 — 컴파일러가 3바이 정수를 알아서 처리해 줍니다:

```cpp
int k = p[N - 1];

for (int i = 0; i < N; i++) {
    k = q[k].idx = p[i];

for (int i = 0; i < N; i++) {
    k = q[k].idx;
```

이 코드는 L1 캐시에서 6.5ns로 측정됩니다. 컴파일러가 선택한 기본 변환 절차가 최적이 아니기 때문에 개선의 여지가 있습니다. 4바이트 정수를 수동으로 로드하고 직접 자를 수 있습니다 (추가적인 1바이트 메모리를 소유하고 있음을 보장하기 위해 `q` 배열에 요소를 하나 더 추가해야 합니다):

```cpp
k = *((int*) (q + k));
k &= ((1<<24) - 1);
```

이제 4ns 만에 실행되며 다음과 같은 그래프를 생성합니다:

![](../img/permutation-bf-custom.svg)

충분히 확대해 보면 ([그래프는 svg입니다](../img/permutation-bf-custom.svg)), 매우 작은 배열에서는 포인터가 우세하다가, L2-L3 캐시 경계 근처부터 커스텀 비트 필드가 역전하기 시작하고, 아주 큰 배열에서는 어차피 캐시 히트가 발생하지 않으므로 큰 차이가 없음을 알 수 있습니다.

이것은 5배의 개선을 가져다주는 종류의 최적화는 아니지만, 다른 모든 리소스가 소진되었을 때 시도해 볼 만한 가치가 있습니다.
