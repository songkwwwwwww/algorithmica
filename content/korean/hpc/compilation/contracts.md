Java나 Rust 같은 "안전한" 언어에서는 일반적으로 가능한 모든 연산과 입력에 대해 잘 정의된 동작을 가집니다. 해시 테이블의 키 순서나 `std::vector`의 증가 계수와 같이 *미정의(under-defined)*된 것들이 일부 있지만, 이는 대개 향후 잠재적인 성능 향상을 위해 구현 방식에 맡겨진 사소한 세부 사항입니다.

반면, C와 C++는 정의되지 않은 동작(undefined behavior, UB)의 개념을 다른 차원으로 끌어올립니다. 특정 연산들은 컴파일이나 런타임 중에 오류를 발생시키지 않지만, 단지 *허용되지 않을* 뿐입니다 — 이는 프로그래머와 컴파일러 사이의 *계약*과 같아서, 정의되지 않은 동작이 발생하는 경우 컴파일러는 말 그대로 모니터를 폭파하거나 하드 드라이브를 포맷하는 것을 포함하여 무엇이든 할 수 있도록 법적으로 허용됩니다. 하지만 컴파일러 엔지니어들은 그런 일에는 관심이 없습니다. 대신, 정의되지 않은 동작은 코너 케이스가 없음을 보장하고 최적화를 돕는 데 사용됩니다.

### 정의되지 않은 동작이 존재하는 이유

정의되지 않은 동작을 유발하는 두 가지 주요 작업 그룹이 있습니다:

- 0으로 나누기, 널 포인터 역참조, 또는 초기화되지 않은 메모리 읽기와 같이 거의 확실히 의도하지 않은 버그인 연산들입니다. 이러한 버그는 테스트 중에 가능한 한 빨리 발견하고 싶을 것이므로, 항상 0을 반환하는 것과 같은 고정된 폴백 동작을 수행하는 것보다 프로그램이 충돌하거나 비결정적인 동작을 보이는 것이 더 낫습니다.

  *새니타이저(sanitizers)*를 사용하여 프로그램을 컴파일하고 실행하면 정의되지 않은 동작을 조기에 발견할 수 있습니다. GCC and Clang에서는 `-fsanitize=undefined` 플래그를 사용할 수 있으며, UB를 유발하는 것으로 악명 높은 일부 연산들이 런타임에 이를 감지하도록 계측(instrumented)됩니다.

- 플랫폼마다 관찰 가능한 동작이 약간씩 다른 연산들입니다. 예를 들어, 정수를 31비트 이상 왼쪽으로 시프트하는 결과는 정의되지 않았는데, 이는 해당 명령어가 Arm과 x86 CPU에서 다르게 구현되어 있기 때문입니다. 특정 동작 하나를 표준화하면 다른 플랫폼용으로 컴파일된 모든 프로그램은 해당 엣지 케이스를 확인하기 위해 몇 사이클을 더 소비해야 하므로, 이를 정의되지 않은 채로 두는 것이 최선입니다.

  때때로 특정 플랫폼 전용 동작에 대한 정당한 사용 사례가 있는 경우, 이를 정의되지 않은 것으로 선언하는 대신 *구현 정의(implementation-defined)*로 남겨둘 수 있습니다. 예를 들어, [음수 정수](/hpc/arithmetic/integer)를 오른쪽으로 시프트한 결과는 플랫폼에 따라 다릅니다: 0이 들어오거나 부호 비트가 들어옵니다 (예: `11010110 = -42`를 오른쪽으로 한 비트 시프트하는 것은 `01101011 = 107` 또는 `11101011 = -21`을 의미할 수 있으며, 두 사례 모두 현실적입니다).

어떤 것을 구현 정의 동작 대신 정의되지 않은 동작으로 지정하는 것은 컴파일러의 최적화에도 도움이 됩니다. 부호 있는 정수 오버플로(signed integer overflow)의 경우를 생각해 보십시오. 거의 모든 아키텍처에서 [부호 있는 정수](/hpc/arithmetic/integer)는 부호 없는 정수와 동일하게 오버플로되어 `INT_MAX + 1 == INT_MIN`이 되지만, C++ 표준에 따르면 이는 정의되지 않은 동작입니다. 이는 매우 의도적인 것입니다: 부호 있는 정수 오버플로를 허용하지 않으면, `(x + 1) > x`는 `int`에 대해 항상 참임이 보장되지만, 오버플로가 발생할 수 있는 `unsigned int`에 대해서는 그렇지 않습니다. 부호 있는 타입의 경우, 이를 통해 컴파일러는 이러한 체크를 최적화하여 제거할 수 있습니다.

더 자연스럽게 발생하는 예로, 정수 제어 변수가 있는 루프의 경우를 생각해 보십시오. 현대 C++와 Rust 같은 언어들은 프로그래머에게 부호 없는 정수(`size_t` / `usize`)를 사용하도록 권장하는 반면, C 프로그래머들은 고집스럽게 `int`를 계속 사용합니다. 그 이유를 이해하기 위해 다음 `for` 루프를 살펴보십시오:

```cpp
for (unsigned int i = 0; i < n; i++) {
    // ...
}
```

이 루프는 몇 번 실행될까요? 기술적으로 두 가지 유효한 답이 있습니다: $n$번과 무한대입니다. 무한대는 $n$이 $2^{32}$를 초과하여 $i$가 $2^{32}$번 반복할 때마다 0으로 재설정되는 경우입니다. 전자가 프로그래머가 가정한 상황이겠지만, 언어 사양을 준수하기 위해 컴파일러는 여전히 추가적인 런타임 체크를 삽입하고 서로 다르게 최적화되어야 하는 두 가지 케이스를 고려해야 합니다. 한편, `int` 버전은 부호 있는 오버플로의 가능성 자체가 존재하지 않는 것으로 정의되어 있으므로 정확히 $n$번 반복하게 됩니다.

### 코너 케이스 제거 (Removing Corner Cases)

"안전한" 프로그래밍 스타일은 대개 많은 런타임 체크를 수반하지만, 이것이 반드시 성능 저하로 이어질 필요는 없습니다.

예를 들어, Rust는 배열 및 기타 랜덤 액세스 구조를 인덱싱할 때 범위 검사(bounds checking)를 사용하는 것으로 유명합니다. C++ STL에서 `vector`와 `array`는 "안전하지 않은" `[]` 연산자와 다음과 같은 "안전한" `.at()` 메서드를 가집니다:

```cpp
T at(size_t k) {
    if (k >= size())
        throw std::out_of_range("Array index exceeds its size");
    return _memory[k];
}
```

흥미롭게도, 컴파일러가 컴파일 타임에 각 액세스가 범위 내에 있음을 증명할 수 있는 경우가 많기 때문에 이러한 체크가 런타임 중에 실제로 실행되는 경우는 드뭅니다. 예를 들어, `for` 루프에서 1부터 배열 크기까지 반복하며 매 단계마다 $i$번째 요소를 인덱싱할 때, 불법적인 일은 일어날 수 없으므로 범위 검사는 안전하게 최적화되어 제거될 수 있습니다.

### 가정 (Assumptions)

컴파일러가 코너 케이스의 부재를 증명할 수 없지만 *여러분*은 할 수 있는 경우, 정의되지 않은 동작 메커니즘을 사용하여 이 추가 정보를 제공할 수 있습니다.

Clang에는 반드시 참임이 보장되는 문장을 넣을 수 있는 유용한 `__builtin_assume` 함수가 있으며, 컴파일러는 이 가정을 최적화에 사용합니다. GCC에서는 `__builtin_unreachable`을 사용하여 동일한 작업을 수행할 수 있습니다:

```cpp
void assume(bool pred) {
    if (!pred)
        __builtin_unreachable();
}
```

예를 들어, 위 예제의 `at` 앞에 `assume(k < vector.size())`를 넣으면 범위 검사가 최적화되어 제거됩니다.

버그를 찾기 위해 `assume`을 `assert` 및 `static_assert`와 결합하는 것도 매우 유용합니다. 동일한 함수를 사용하여 디버그 빌드에서는 전제 조건을 확인하고, 프로덕션 빌드에서는 성능 향상을 위해 이를 사용할 수 있습니다.

### 산술 (Arithmetic)

코너 케이스는 특히 산술을 최적화할 때 염두에 두어야 할 사항입니다.

[부동 소수점 산술](/hpc/arithmetic/float)의 경우, `-ffast-math` 플래그( `-Ofast`에도 포함됨)를 사용하여 엄격한 표준 준수를 비활성화할 수 있으므로 걱정이 덜합니다. 사실 그렇게 해야만 합니다. 그렇지 않으면 컴파일러는 어떠한 최적화도 없이 소스 코드와 동일한 순서로 산술 연산을 실행할 수밖에 없기 때문입니다.

<!--

because even algebraically correct rearrangements result in slightly different rounding errors

-->

정수 산술의 경우 결과가 항상 정확해야 하므로 상황이 다릅니다. 2로 나누는 경우를 생각해 보십시오:

```cpp
unsigned div_unsigned(unsigned x) {
    return x / 2;
}
```

널리 알려진 최적화는 이를 단일 오른쪽 시프트(`x >> 1`)로 대체하는 것입니다:

```nasm
shr eax
```

이는 모든 *양수*에 대해 분명히 옳지만, 일반적인 경우는 어떨까요?

```cpp
int div_signed(int x) {
    return x / 2;
}
```

`x`가 음수이면 단순히 시프트하는 것은 작동하지 않습니다 — 0으로 채우든 부호 비트로 채우든 상관없이 말이죠:

- 0으로 채우면 음수가 아닌 결과가 나옵니다(부호 비트가 0이 됨).
- 부호 비트로 채우면 0 방향이 아닌 음의 무한대 방향으로 반올림이 발생합니다 (`-5 / 2`는 `-2`가 아니라 `-3`이 됩니다)[^python].

[^python]: 흥미로운 사실: 파이썬에서는 어떤 이유에서인지 음수를 정수 나눗셈하면 결과를 내림(floor)합니다. 그래서 `-5 // 2 = -3`이며, 이는 `-5 >> 1 = -3`과 동일합니다. 귀도 반 로섬이 언어를 처음 설계할 때 이 최적화를 염두에 두었는지는 의문이지만, 이론적으로 2로 나누는 연산이 많은 [JIT 컴파일된](/hpc/complexity/languages/#compiled-languages) 파이썬 프로그램은 유사한 C++ 프로그램보다 빠를 수 있습니다.

따라서 일반적인 경우에는 이를 작동하게 하기 위해 몇 가지 보조 수단을 삽입해야 합니다:

```nasm
mov  ebx, eax
shr  ebx, 31    ; 부호 비트 추출
add  eax, ebx   ; 음수인 경우 값에 1을 더해 0 방향으로 반올림되도록 함
sar  eax        ; 부호 비트로 채우며 시프트
```

양수인 경우만 의도된 것이라면, `assume` 메커니즘을 사용하여 음수 `x`의 가능성을 배제하고 이 코너 케이스 처리를 피할 수 있습니다:

```cpp
int div_assume(int x) {
    assume(x >= 0);
    return x / 2;
}
```

비록 이 특정한 경우에는 음수가 아닌 숫자만 기대한다는 것을 표현하는 가장 좋은 구문은 부호 없는 정수 타입을 사용하는 것이겠지만요.

이와 같은 뉘앙스 때문에, 컴파일러가 해주기를 바라는 것보다 중간 함수에서 대수식을 확장하고 산술 연산을 수동으로 직접 단순화하는 것이 이득인 경우가 많습니다.

### 메모리 앨리어싱 (Memory Aliasing)

컴파일러는 메모리 읽기 및 쓰기와 관련된 연산을 최적화하는 데 상당히 서툽니다. 최적화가 올바른지 판단하기 위한 문맥이 부족한 경우가 많기 때문입니다.

다음 예제를 살펴보십시오:

```c++
void add(int *a, int *b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

이 루프의 각 반복은 독립적이므로 병렬로 실행되거나 [벡터화](/hpc/simd)될 수 있습니다. 하지만 기술적으로 그렇게 될까요?

배열 `a`와 `b`가 겹치는 경우 문제가 발생할 수 있습니다. `b == a + 1`인 경우, 즉 `b`가 두 번째 요소부터 시작하는 `a`의 메모리 뷰인 경우를 생각해 보십시오. 이 경우 다음 반복은 이전 반복에 의존하게 되며, 유일하게 올바른 해결책은 루프를 순차적으로 실행하는 것입니다. 프로그래머는 그런 일이 일어날 수 없음을 알고 있더라도 컴파일러는 그러한 가능성을 확인해야 합니다.

이것이 바로 `const`와 `restrict` 키워드가 있는 이유입니다. 첫 번째는 포인터 변수로 메모리를 수정하지 않음을 강제하고, 두 번째는 메모리가 겹치지(aliased) 않음을 컴파일러에 알리는 방법입니다.

```cpp
void add(int * __restrict__ a, const int * __restrict__ b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

이러한 키워드들은 자체 문서화 목적으로도 사용하는 것이 좋습니다.

### C++ 계약 (C++ Contracts)

계약 프로그래밍은 충분히 활용되지 않고 있지만 매우 강력한 기법입니다.

C++ 표준에 [계약 속성(contract attributes)](http://www.hellenico.gr/cpp/w/cpp/language/attributes/contract.html)의 형태로 계약 기반 설계(design-by-contract)를 추가하려는 후기 제안이 있으며, 이는 기능적으로 우리가 만든 컴파일러 전용 `assume`과 동일합니다:

```c++
T at(size_t k) [[ expects: k < n ]] {
    return _memory[k];
}
```

속성에는 `expects`, `ensures`, `assert`의 세 가지 유형이 있으며, 각각 함수의 전제 조건과 사후 조건 지정, 그리고 프로그램 어디에나 넣을 수 있는 일반적인 단언(assertion)에 사용됩니다.

불행히도 이 흥미롭고 새로운 기능은 주요 C++ 컴파일러에 구현되기는커녕 [아직 최종 표준화되지도 않았습니다](https://www.reddit.com/r/cpp/comments/cmk7ek/what_happened_to_c20_contracts/). 하지만 아마도 몇 년 안에 다음과 같은 코드를 작성할 수 있게 될 것입니다:

```c++
bool is_power_of_two(int m) {
    return m > 0 && (m & (m - 1) == 0);
}

int mod_power_of_two(int x, int m)
    [[ expects: x >= 0 ]]
    [[ expects: is_power_of_two(m) ]]
    [[ ensures r: r >= 0 && r < m ]]
{
    int r = x & (m - 1);
    [[ assert: r = x % m ]];
    return r;
}
```

일부 형태의 계약 프로그래밍은 [Rust](https://docs.rs/contracts/latest/contracts/) 및 [D](https://dlang.org/spec/contracts.html)와 같은 다른 성능 지향 언어에서도 사용할 수 있습니다.

언어에 구애받지 않는 일반적인 조언은 항상 컴파일러가 생성한 [어셈블리를 검사](../stages)하고, 결과가 기대와 다르다면 컴파일러의 최적화를 제한하고 있을 수 있는 코너 케이스에 대해 생각해 보라는 것입니다.
