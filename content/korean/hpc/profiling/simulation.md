이러한 프로파일러에는 시뮬레이션되는 계산의 측면에 따라 많은 하위 범주가 있습니다. 이 글에서는 [캐싱](/hpc/cpu-cache)과 [분기 예측](/hpc/pipelining/branching)에 초점을 맞추고, 이를 위해 [Cachegrind](https://valgrind.org/docs/manual/cg-manual.html)를 사용할 것입니다. Cachegrind는 메모리 누수 탐지 및 전반적인 메모리 디버깅을 위한 잘 알려진 도구인 [Valgrind](https://valgrind.org/)의 프로파일링 중심 구성 요소입니다.

### Cachegrind를 이용한 프로파일링

Cachegrind는 기본적으로 바이너리에서 메모리 읽기/쓰기 및 조건부/간접 점프를 수행하는 "흥미로운" 명령(instruction)들을 검사하고, 이를 소프트웨어 데이터 구조를 사용하여 해당 하드웨어 작업을 시뮬레이션하는 코드로 대체합니다. 따라서 소스 코드에 접근할 필요 없이 이미 컴파일된 프로그램에서 작동할 수 있으며, 다음과 같이 모든 프로그램에서 실행할 수 있습니다.

```bash
valgrind --tool=cachegrind --branch-sim=yes ./run
#       분기 예측도 시뮬레이션하려면 ^   ^ 반드시 하나의 프로세스일 필요는 없는 모든 명령
```

이 도구는 관련된 모든 바이너리를 계측(instrument)하고 실행한 후, [perf stat](../events)과 유사한 요약을 출력합니다.


우리는 [이전 섹션](../events)에서와 동일한 예제 코드를 Cachegrind에 입력했습니다. 백만 개의 무작위 정수 배열을 생성하고 정렬한 다음, 백만 번의 이진 탐색을 수행합니다. Cachegrind는 perf가 측정한 메모리 읽기 및 분기 수가 [투사적 실행(speculative execution)](/hpc/pipelining)으로 인해 약간 부풀려진 것을 제외하고는 perf와 거의 동일한 수치를 보여줍니다. 투사적 실행은 하드웨어에서 실제로 발생하여 하드웨어 카운터를 증가시키지만, 폐기되어 실제 성능에는 영향을 미치지 않으므로 시뮬레이션에서는 무시됩니다.

Cachegrind는 시스템에서 유추된 특성을 가진 첫 번째 단계(`D1`은 데이터, `I1`은 명령용)와 마지막 단계(`LL`, 통합형) 캐시 레벨만 모델링합니다. 하지만 명령줄에서 이를 직접 설정할 수도 있으므로 제약은 없습니다. 예를 들어 L2 캐시를 모델링하려면 `--LL=<size>,<associativity>,<line size>`와 같이 설정할 수 있습니다.

지금까지는 프로그램을 느리게 만들기만 했고 `perf stat`이 제공할 수 없는 정보는 주지 않은 것처럼 보입니다. 요약 정보 이상의 것을 얻으려면 기본적으로 동일한 디렉토리에 `cachegrind.out.<pid>`라는 이름으로 덤프되는 프로파일링 정보 파일인 특수 파일을 검사할 수 있습니다. 이 파일은 사람이 읽을 수 있는 형식이지만, 일반적으로 `cg_annotate` 명령을 통해 읽습니다.

```bash
cg_annotate cachegrind.out.4159404 --show=Dr,D1mr,DLmr,Bc,Bcm
#                                    ^ 데이터 읽기와 분기에만 관심이 있는 경우
```

먼저 캐시 시스템의 특성을 포함하여 실행 중에 사용된 매개변수를 보여줍니다.

```
I1 cache:         32768 B, 64 B, 8-way associative
D1 cache:         32768 B, 64 B, 8-way associative
LL cache:         8388608 B, 64 B, direct-mapped
```

L3 캐시를 정확하게 파악하지는 못했습니다. 통합형이 아니며(총 8M이지만 단일 코어는 4M만 사용) 16-way 연관(associative) 방식이지만, 일단은 무시하겠습니다.

정렬 단계에서 많은 분기 예측 실패가 발생하고, 이진 탐색 중에 L1 캐시 미스와 분기 예측 실패가 모두 많이 발생하는 것을 볼 수 있습니다. perf로는 이러한 정보를 얻을 수 없었습니다. perf는 전체 프로그램에 대한 수치만 알려주기 때문입니다.

Cachegrind의 또 다른 훌륭한 기능은 소스 코드의 행 단위 주석(annotation)입니다. 이를 위해서는 프로그램을 디버그 정보(`-g`)와 함께 컴파일해야 하며, `cg_annotate`에 주석을 달 소스 파일을 명시적으로 알려주거나 `--auto=yes` 옵션을 전달하여 접근 가능한 모든 것(표준 라이브러리 소스 코드 포함)에 주석을 달도록 할 수 있습니다.

따라서 소스 분석의 전체 과정은 다음과 같습니다.

```bash
g++ -O3 -g sort-and-search.cc -o run
valgrind --tool=cachegrind --branch-sim=yes --cachegrind-out-file=cachegrind.out ./run
cg_annotate cachegrind.out --auto=yes --show=Dr,D1mr,DLmr,Bc,Bcm
```

glibc 구현은 가독성이 가장 좋지는 않으므로, 설명을 위해 `lower_bound`를 직접 만든 이진 탐색으로 대체했습니다. 그러면 다음과 같이 주석이 달립니다.

안타깝게도 Cachegrind는 메모리 액세스와 분기만 추적합니다. 병목 현상이 다른 원인으로 인해 발생하는 경우에는 [다른 시뮬레이션 도구](../mca)가 필요합니다.
