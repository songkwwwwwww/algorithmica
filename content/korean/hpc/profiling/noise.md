두 개의 라이브러리 알고리즘 구현체가 각각 자체 벤치마킹 코드를 유지하면서 서로 자기가 더 빠르다고 주장하는 상황은 드물지 않습니다. 이는 관련된 모든 사람, 특히 둘 중 하나를 선택해야 하는 사용자들을 혼란스럽게 만듭니다.

이런 상황은 대개 저자들의 부정직한 행위 때문이 아닙니다. 단지 "빠르다"는 것에 대한 정의가 서로 다르기 때문이며, 실제로 단 하나의 성능 지표만을 정의하고 사용하는 것은 종종 매우 큰 문제를 일으킵니다.

### 올바른 대상 측정하기

벤치마크에 편향(bias)을 유발할 수 있는 요소는 많습니다.

**서로 다른 데이터셋.** 성능이 데이터셋의 분포에 의존하는 알고리즘이 많습니다. 예를 들어 가장 빠른 정렬, 최단 경로, 또는 이진 탐색 알고리즘이 무엇인지 정의하려면 알고리즘이 실행되는 데이터셋을 고정해야 합니다.

이는 단일 입력을 처리하는 알고리즘에도 적용되기도 합니다. 예를 들어, GCD 구현에 순차적인 숫자를 입력하는 것은 좋지 않은데, 이는 분기(branch)를 매우 예측 가능하게 만들기 때문입니다.

```c++
// 이렇게 하지 마세요
int checksum = 0;

for (int a = 0; a < 1000; a++)
    for (int b = 0; b < 1000; b++)
        checksum ^= gcd(a, b);
```

하지만 동일한 숫자들을 무작위로 샘플링하면 분기 예측이 훨씬 어려워지고, 동일한 입력을 순서만 바꿔서 처리함에도 불구하고 벤치마크에 더 오랜 시간이 걸리게 됩니다.

```c++
int a[1000], b[1000];

for (int i = 0; i < 1000; i++)
    a[i] = rand() % 1000, b[i] = rand() % 1000;

int checksum = 0;

for (int t = 0; t < 1000; t++)
    for (int i = 0; i < 1000; i++)
        checksum += gcd(a[i], b[i]);
```

대부분의 경우 가장 논리적인 선택은 데이터를 균등하게 무작위로 샘플링하는 것이지만, 많은 실제 애플리케이션의 분포는 균등함과는 거리가 멀기 때문에 하나만 선택할 수는 없습니다. 일반적으로 좋은 벤치마크는 애플리케이션에 특화되어야 하며, 실제 사용 사례를 최대한 잘 나타내는 데이터셋을 사용해야 합니다.

**다중 목표.** 일부 알고리즘 설계 문제에는 하나 이상의 핵심 목표가 있습니다. 예를 들어 해시 테이블은 키의 분포에 크게 의존할 뿐만 아니라 다음 요소들 사이의 균형을 신중하게 맞춰야 합니다.

- 메모리 사용량,
- 추가(add) 쿼리의 지연 시간,
- 긍정 멤버십(positive membership, 존재하는 키) 쿼리의 지연 시간,
- 부정 멤버십(negative membership, 존재하지 않는 키) 쿼리의 지연 시간.

해시 테이블 구현체들 사이에서 선택하는 유일한 방법은 실제 애플리케이션에 여러 변형을 직접 넣어보는 것입니다.

**지연 시간 vs 처리량.** 사람들이 자주 간과하는 또 다른 측면은 단일 쿼리에 대해서도 실행 시간을 두 가지 이상의 방식으로 정의할 수 있다는 점입니다.

다음과 같은 코드를 작성할 때:

```c++
for (int i = 0; i < N; i++)
    q[i] = rand();

int checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

전체 시간을 측정하고 이를 반복 횟수로 나누면, 실제로는 쿼리의 *처리량 (throughput)*, 즉 단위 시간당 처리할 수 있는 연산의 수를 측정하는 것입니다. 이는 대개 연산들이 인터리빙(interleaving)되어 실행되기 때문에 개별 연산을 따로 처리하는 데 걸리는 시간보다 적게 걸립니다.

실제 *지연 시간 (latency)*을 측정하려면 호출 사이에 의존성을 도입해야 합니다.

```c++
for (int i = 0; i < N; i++)
    checksum ^= lower_bound(checksum ^ q[i]);
```

이는 파이프라인 스톨(stall) 문제가 발생할 수 있는 알고리즘(예: 분기가 있는 알고리즘과 분기가 없는 알고리즘을 비교할 때)에서 대개 가장 큰 차이를 만듭니다.

**콜드 캐시 (Cold Cache).** 편향의 또 다른 원인은 *콜드 캐시 효과*입니다. 필요한 데이터가 아직 캐시에 없기 때문에 초기 메모리 읽기에 더 많은 시간이 걸리는 현상입니다.

이는 측정을 시작하기 전에 *웜업 실행 (warm-up run)*을 수행함으로써 해결할 수 있습니다.

```c++
// 웜업 실행

volatile checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);


// 실제 실행

clock_t start = clock();
checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

체크섬 계산보다 더 복잡한 검증이 필요한 경우, 웜업 실행을 정답 검증과 결합하는 것도 편리한 방법입니다.

**과도한 최적화 (Over-optimization).** 때때로 컴파일러가 벤치마킹 대상 코드를 아예 없애버려 벤치마크 자체가 완전히 잘못되는 경우가 있습니다. 컴파일러가 지름길을 택하지 못하도록 체크섬을 추가하고 이를 어딘가에 출력하거나, 루프 반복의 인터리빙을 방지하는 `volatile` 한정자를 추가해야 합니다.

데이터만 쓰는 알고리즘의 경우, `__sync_synchronize()` 인트린직(intrinsic)을 사용하여 메모리 펜스(memory fence)를 추가함으로써 컴파일러가 업데이트를 누적하지 못하도록 할 수 있습니다.

지금까지 설명한 문제들은 측정에 *편향 (bias)*을 발생시킵니다. 즉, 일관되게 한 알고리즘이 다른 알고리즘보다 유리하게 만듭니다. 벤치마킹에는 예측 불가능한 왜곡이나 완전히 무작위적인 노이즈를 발생시켜 *분산 (variance)*을 증가시키는 다른 유형의 문제들도 있습니다.

이러한 문제들은 주로 부수 효과나 외부 노이즈, 특히 다른 프로세스의 간섭(noisy neighbors)이나 CPU 주파수 스케일링으로 인해 발생합니다.

- 연산 중심(compute-bound) 알고리즘을 벤치마킹한다면 `perf stat`을 사용하여 사이클 단위로 성능을 측정하세요. 이렇게 하면 노이즈의 주요 원인인 클럭 주파수의 변동으로부터 독립적인 결과를 얻을 수 있습니다.
- 그렇지 않다면 코어 주파수를 예상 수치로 고정하고 아무것도 간섭하지 않도록 하세요. 리눅스에서는 `cpupower`를 사용할 수 있습니다(예: 최소 주파수로 설정하려면 `sudo cpupower frequency-set -g powersave`, 터보 부스트를 활성화하려면 `sudo cpupower frequency-set -g ondemand`). 저는 이를 위한 버튼이 별도로 있는 [편리한 GNOME 쉘 확장 프로그램](https://extensions.gnome.org/extension/1082/cpufreq/)을 사용합니다.
- 가능하다면 하이퍼스레딩(hyper-threading)을 끄고 작업을 특정 코어에 할당하세요. 시스템에서 다른 작업이 실행되지 않도록 하고, 네트워크를 끄고 마우스를 건드리지 않도록 노력하세요.

노이즈와 편향을 완전히 제거할 수는 없습니다. 심지어 프로그램의 이름조차 속도에 영향을 줄 수 있습니다. 실행 파일의 이름은 환경 변수에 들어가고, 환경 변수는 콜 스택에 쌓이므로 이름의 길이는 스택 정렬(stack alignment)에 영향을 미칩니다. 이는 캐시 라인이나 메모리 페이지 경계를 가로지르는 데이터 접근을 발생시켜 속도를 늦출 수 있습니다.

최적화 방향을 정하거나 특히 다른 사람에게 결과를 보고할 때 노이즈를 고려하는 것이 중요합니다. 2배 정도의 개선을 기대하는 것이 아니라면, 모든 마이크로벤치마크를 A/B 테스트와 동일한 방식으로 취급하세요.

노트북에서 1초 미만으로 프로그램을 실행할 때 ±5%의 성능 변동은 완전히 정상입니다. 따라서 잠재적인 +1% 개선 사항을 유지할지 되돌릴지 결정하고 싶다면, 분산과 p-값(p-values)을 계산하여 통계적 유의성에 도달할 때까지 실행을 반복하세요.
