CPU가 조건부 점프 또는 [다른 유형의 분기](/hpc/architecture/indirect)를 만나면, 조건이 계산될 때까지 단순히 대기하지 않습니다. 대신, 즉시 실행될 가능성이 더 높아 보이는 분기를 *투기적으로 실행(speculatively executing)*하기 시작합니다. 실행 중에 CPU는 각 명령어에서 수행된 분기에 대한 통계를 계산하고, 시간이 지난 후에는 공통 패턴을 인식하여 이를 예측하기 시작합니다.

이러한 이유로 분기의 진정한 "비용"은 CPU가 이를 얼마나 잘 예측할 수 있는지에 따라 크게 달라집니다. 만약 순수하게 50/50의 확률이라면, [제어 해저드(control hazard)](../hazards)를 겪고 전체 파이프라인을 폐기해야 하며, 다시 구축하는 데 15-20 사이클이 더 소요됩니다. 반면 분기가 항상 실행되거나 절대 실행되지 않는다면, 조건을 확인하는 것 외에는 거의 아무런 비용도 들지 않습니다.

## 실험

사례 연구로, 0에서 99 사이의 랜덤 정수 배열을 생성해 보겠습니다:

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;
```

그런 다음 50보다 작은 모든 요소를 합산하는 루프를 만듭니다:

```c++
volatile int s;

for (int i = 0; i < N; i++)
    if (a[i] < 50)
        s += a[i];
```

$N = 10^6$으로 설정하고 이 루프를 여러 번 실행하여 [콜드 캐시(cold cache)](/hpc/cpu-cache/bandwidth) 효과가 결과를 방해하지 않도록 합니다. 누산기 변수를 `volatile`로 표시하여 컴파일러가 루프를 벡터화하거나, 반복을 인터리빙하거나, 다른 방식으로 "속임수"를 쓰지 못하도록 합니다.

Clang에서 이는 다음과 같은 어셈블리를 생성합니다:

```nasm
    mov  rcx, -4000000
    jmp  body
counter:
    add  rcx, 4
    jz   finished   ; "rcx가 0이 되면 점프"
body:
    mov  edx, dword ptr [rcx + a + 4000000]
    cmp  edx, 49
    jg   counter
    add  dword ptr [rsp + 12], edx
    jmp  counter
```

우리의 목표는 완전히 예측 불가능한 분기를 시뮬레이션하는 것이며, 이를 성공적으로 달성했습니다. 코드는 요소당 약 14 CPU 사이클이 소요됩니다. 대략적인 추정치를 위해 분기가 `<`와 `>=` 사이를 번갈아 가며 발생하고, 파이프라인이 매 반복마다 잘못 예측된다고 가정해 보겠습니다. 그러면 매 두 번의 반복마다:

- 파이프라인을 폐기합니다. Zen 2에서는 파이프라인 깊이가 19단계입니다(즉, 19개의 스테이지가 있고 각 스테이지는 1사이클이 소요됨).
- 메모리 인출과 비교가 필요하며, 비용은 약 5 사이클입니다. 짝수 및 홀수 반복의 조건을 동시에 확인할 수 있으므로, 2회 반복당 한 번만 지불한다고 가정합시다.
- `<` 분기의 경우, `a[i]`를 휘발성(메모리에 저장된) 변수 `s`에 더하는 데 약 4 사이클이 더 필요합니다.

따라서 평균적으로 요소당 $(4 + 5 + 19) / 2 = 14$ 사이클을 소비해야 하며, 이는 측정값과 일치합니다.

### 분기 예측 (Branch Prediction)

하드코딩된 `50`을 `<` 분기의 확률을 설정하는 조정 가능한 매개변수 `P`로 바꿀 수 있습니다:

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P)
        s += a[i];
```

이제 다양한 `P` 값에 대해 벤치마킹을 수행하면 흥미로운 그래프가 나타납니다:

![](../img/probabilities.svg)

예상대로 50-55%에서 정점을 찍습니다. 분기 예측 오류가 여기서 가장 비용이 많이 드는 부분이기 때문입니다. 이 그래프는 비대칭적입니다. 조건이 절대 충족되지 않는 경우(`P = 0`) 조건을 확인하는 데는 약 1 사이클만 소요되고, 분기가 항상 실행되는 경우(`P = 100`) 합계에는 약 7 사이클이 소요됩니다.

이 그래프는 단봉형(unimodal)이 아닙니다. 약 85-90% 부근에 또 다른 로컬 최솟값이 있습니다. 거기서는 요소당 약 6.15 사이클을 소비하며, 이는 분기가 항상 실행될 때보다 약 10-15% 더 빠릅니다. 이는 더 적은 덧셈을 수행해야 한다는 사실을 반영합니다. 이 시점에서는 분기 예측 오류가 성능에 영향을 미치지 않는데, 오류가 발생해도 전체 명령어 버퍼가 폐기되는 것이 아니라 투기적으로 스케줄링된 연산만 폐기되기 때문입니다. 본질적으로 그 10-15%의 예측 오류율은 파이프라인에서 스톨이 발생하지 않을 정도로 멀리 내다볼 수 있으면서도, 더 저렴한 `>=` 분기를 취함으로써 10-15%를 절약할 수 있는 평형점입니다.

거의 발생하지 않는 조건을 확인하는 데는 거의 비용이 들지 않는다는 점에 주목하세요. 이것이 프로그래머들이 런타임 예외와 기본 케이스 체크를 그렇게 많이 사용하는 이유입니다. 실제로 드물게 발생한다면 실질적인 비용이 들지 않기 때문입니다.

### 패턴 감지 (Pattern Detection)

우리의 예에서 효율적인 분기 예측을 위해 필요했던 것은 하드웨어 통계 카운터뿐입니다. 역사적으로 분기 B보다 분기 A를 더 자주 택했다면, 분기 A를 투기적으로 실행하는 것이 합리적입니다. 하지만 현대 CPU의 분기 예측기는 그보다 훨씬 더 정교하며 훨씬 더 복잡한 패턴을 감지할 수 있습니다.

`P`를 다시 50으로 고정하고, 메인 합계 루프 전에 배열을 먼저 정렬해 보겠습니다:

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;

std::sort(a, a + n);
```

우리는 여전히 같은 요소를 다른 순서로 처리하고 있을 뿐이지만, 14 사이클 대신 4 사이클보다 조금 더 긴 시간에 실행됩니다. 이는 순수 `<` 및 `>=` 분기 비용의 정확한 평균입니다.

분기 예측기는 단순히 "계속 예, 그 다음 계속 아니오" 또는 "예-아니오-예-아니오"보다 훨씬 더 복잡한 패턴을 포착할 수 있습니다. 배열 크기 $N$을 1000으로 줄이면(정렬하지 않고), 분기 예측기는 비교 시퀀스 전체를 암기하며 벤치마크는 다시 약 4 사이클로 측정됩니다. 사실 정렬된 배열의 경우보다 약간 더 적게 걸리기도 하는데, 정렬된 경우에는 분기 예측기가 "계속 예"와 "계속 아니오" 상태 사이를 전환하는 데 시간을 써야 하기 때문입니다.

### 분기 가능성 힌트 주기 (Hinting Likeliness of Branches)

어떤 분기가 더 가능성이 높은지 미리 알고 있다면, 컴파일러에 [그 정보를 전달하는 것](/hpc/compilation/situational)이 유익할 수 있습니다:

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P) [[likely]]
        s += a[i];
```

`P = 75`일 때 요소당 약 7.3 사이클로 측정되는 반면, 힌트가 없는 원래 버전은 약 8.3 사이클이 필요합니다.

이 힌트는 분기를 제거하거나 분기 예측기에 무언가를 전달하지는 않지만, CPU 프런트엔드가 더 가능성이 높은 분기를 약간 더 빨리 처리할 수 있도록 [기계어 코드 레이아웃](/hpc/architecture/layout)을 변경합니다 (보통 1사이클 이내의 차이입니다).

이 최적화는 컴파일 단계 전에 어떤 분기가 더 자주 발생할지 알고 있을 때만 유용합니다. 분기가 근본적으로 예측 불가능할 때는 *조건부 실행(predication)*을 사용하여 분기를 완전히 제거할 수 있습니다. 이는 [다음 섹션](../branchless)에서 살펴볼 매우 중요한 기술입니다.
