*지연 시간(latency)*을 최적화하는 것은 보통 *처리량(throughput)*을 최적화하는 것과는 상당히 다릅니다:

- 데이터 구조 쿼리나 작은 단발성 또는 분기 위주의 알고리즘을 최적화할 때는 명령어의 [지연 시간](../tables)을 찾아보고, 계산의 실행 그래프를 머릿속으로 그려본 다음, 크리티컬 패스(critical path)가 더 짧아지도록 재구성해야 합니다. <!-- [Binary GCD](/hpc/algorithms/gcd) is a good example of that. -->
- 핫 루프(hot loops)나 대규모 데이터셋 알고리즘을 최적화할 때는 명령어의 처리량을 찾아보고, 반복(iteration)당 각 명령어가 몇 번 사용되는지 세어보고, 그중 어떤 것이 병목인지 결정한 다음, 해당 명령어가 덜 사용되도록 루프를 재구성해야 합니다.

마지막 조언은 각 반복이 이전 반복과 완전히 독립적인 *데이터 병렬(data-parallel)* 루프에서만 작동합니다. 연속된 반복 사이에 상호 의존성이 있는 경우, 다음 반복이 이전 반복의 완료를 기다리느라 [데이터 해저드](../hazards)로 인한 파이프라인 스톨(stall)이 발생할 수 있습니다.

### 예제

간단한 예로 배열의 합을 구하는 방식을 생각해 봅시다:

```c++
int s = 0;

for (int i = 0; i < n; i++)
    s += a[i];
```

잠시 컴파일러가 이 루프를 [벡터화](/hpc/simd)하지 않고, [메모리 대역폭](/hpc/cpu-cache/bandwidth)은 고려 대상이 아니며, 루프 변수 유지와 관련된 추가 비용을 지불하지 않도록 루프가 [언롤링(unrolled)](/hpc/architecture/loops)되었다고 가정해 보겠습니다. 이 경우 계산은 매우 단순해집니다:

```c++
int s = 0;
s += a[0];
s += a[1];
s += a[2];
s += a[3];
// ...
```

이를 얼마나 빨리 계산할 수 있을까요? 정확히 요소당 1 사이클입니다. 매 반복마다 `s`에 다른 값을 더(`add`)하기 위해 1 사이클이 필요하기 때문입니다. CPU가 미리 읽기를 시작할 수 있으므로 메모리 읽기의 지연 시간은 중요하지 않습니다.

하지만 그보다 더 높일 수 있습니다. 제 CPU(Zen 2)에서 `add`의 *처리량*[^throughput]은 2입니다. 즉, 이론적으로 매 사이클마다 두 개의 `add`를 실행할 수 있습니다. 하지만 지금은 불가능합니다. `s`가 $i$번째 요소를 누적하는 데 사용되는 동안에는 적어도 1 사이클 동안 $(i+1)$번째 요소를 위해 사용될 수 없기 때문입니다.

[^throughput]: 레지스터-레지스터 `add`의 처리량은 4이지만, 두 번째 피연산자를 메모리에서 읽어오기 때문에 Zen 2에서 2인 메모리 `mov`의 처리량에 의해 병목이 발생합니다.

해결책은 *두 개의* 누산기를 사용하여 홀수 번째 요소와 짝수 번째 요소를 따로 합산하는 것입니다:

```c++
int s0 = 0, s1 = 0;
s0 += a[0];
s1 += a[1];
s0 += a[2];
s1 += a[3];
// ...
int s = s0 + s1;
```

이제 우리의 슈퍼스칼라 CPU는 이 두 "스레드"를 동시에 실행할 수 있으며, 우리의 계산에는 더 이상 처리량을 제한하는 크리티컬 패스가 존재하지 않습니다.

### 일반적인 경우

명령어의 지연 시간이 $x$이고 처리량이 $y$라면, 이를 포화시키기 위해 $x \cdot y$개의 누산기를 사용해야 합니다. 이는 또한 그 값을 유지하기 위해 $x \cdot y$개의 논리 레지스터가 필요함을 의미하며, 이는 CPU 설계에서 중요한 고려 사항으로, 지연 시간이 긴 명령어에 대해 사용할 수 있는 실행 유닛의 최대 수를 제한하게 됩니다.

이 기술은 주로 [SIMD](/hpc/simd)에서 사용되며 스칼라 코드에서는 잘 사용되지 않습니다. 위의 코드를 [일반화](/hpc/simd/reduction)하여 합계나 다른 리덕션(reductions)을 컴파일러보다 더 빠르게 계산할 수 있습니다.

일반적으로 루프를 최적화할 때는 최대한 활용하고 싶은 하나 또는 몇 개의 *실행 포트(execution ports)*가 있으며, 그 포트들을 중심으로 루프의 나머지 부분을 설계합니다. 서로 다른 명령어들이 서로 다른 포트 집합을 사용할 수 있기 때문에, 어떤 포트가 과도하게 사용될지 항상 명확한 것은 아닙니다. 이런 상황에서는 작은 어셈블리 루프의 병목 지점을 찾는 데 [기계어 코드 분석기](/hpc/profiling/mca)가 매우 도움이 될 수 있습니다.
