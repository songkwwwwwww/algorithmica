메모리 작업 측면에서 알고리즘의 성능을 정확하게 평가하려면 캐시 시스템의 여러 특성을 고려해야 합니다. 캐시 계층의 수, 각 계층의 [메모리 및 블록 크기](../hierarchy), 각 계층에서 사용되는 정확한 [교체 전략](../policies), 때로는 [메모리 페이징](../virtual) 메커니즘의 세부 사항까지 포함됩니다.

알고리즘 설계의 첫 단계에서는 이러한 세부 사항을 추상화하는 것이 큰 도움이 됩니다. 이론적인 캐시 적중률(cache hit rate)을 계산하는 대신, 캐시 성능을 좀 더 질적인 용어로 추론하는 것이 더 합리적인 경우가 많습니다.

이 문서에서는 외부 메모리 모델을 위한 알고리즘 설계를 계속하며, 캐시 시스템의 일부 세부 정보를 알 수 없을 때 I/O 성능을 평가하는 문제를 다룹니다.

이러한 맥락에서 캐시 재사용 정도에 대해 주로 두 가지 방식으로 이야기할 수 있습니다.

- **시간 지역성(Temporal locality)**: 상대적으로 짧은 시간 내에 동일한 데이터에 반복적으로 액세스하여, 요청 사이에 데이터가 캐시에 남아 있을 가능성이 높은 경우를 말합니다.
- **공간 지역성(Spatial locality)**: 메모리 위치상 서로 상대적으로 가까운 요소들을 사용하여, 동일한 메모리 블록 내에 함께 배치되어 한 번에 가져올 가능성이 높은 경우를 말합니다.

다시 말해, 시간 지역성은 동일한 메모리 위치가 곧 다시 요청될 가능성이 높은 경우이고, 공간 지역성은 근처의 위치가 바로 다음에 요청될 가능성이 높은 경우입니다.

이 섹션에서는 이러한 상위 수준의 개념이 실제 최적화에 어떻게 도움이 되는지 몇 가지 사례를 통해 살펴보겠습니다.

### 깊이 우선 vs. 너비 우선 (Depth-First vs. Breadth-First)

병합 정렬과 같은 분할 정복(divide-and-conquer) 알고리즘을 고려해 보겠습니다. 이를 구현하는 데는 두 가지 접근 방식이 있습니다.

- 재귀적으로, 즉 "깊이 우선(depth-first)" 방식으로 구현할 수 있습니다. 일반적으로 구현되는 방식인데, 왼쪽 절반을 정렬하고 오른쪽 절반을 정렬한 다음 결과를 병합합니다.
- 반복적으로, 즉 "너비 우선(breadth-first)" 방식으로 구현할 수 있습니다. 가장 낮은 "계층"을 먼저 처리하는데, 전체 데이터셋을 훑으며 홀수 번째 요소와 짝수 번째 요소를 비교하고, 그다음 처음 두 요소를 다음 두 요소와 병합하는 식입니다.

두 번째 접근 방식이 더 번거로워 보이지만 더 빠를 것 같습니다. 재귀는 항상 느리니까요, 그렇죠?

일반적으로 재귀가 [실제로 느린](/hpc/architecture/functions) 것은 맞지만, 이 알고리즘이나 유사한 많은 분할 정복 알고리즘의 경우에는 그렇지 않습니다. 반복적 접근 방식은 순차적 I/O만 수행한다는 장점이 있지만, 재귀적 접근 방식은 훨씬 더 나은 시간 지역성을 가집니다. 세그먼트가 캐시에 완전히 들어가면, 그 아래의 모든 재귀 계층에 대해 캐시에 머물게 되어 나중에 액세스 시간이 훨씬 빨라집니다.

실제로 이 상태가 될 때까지 배열을 $O(\log \frac{N}{M})$번만 분할하면 되므로 총 $O(\frac{N}{B} \log \frac{N}{M})$개의 블록만 읽으면 됩니다. 반면 반복적 접근 방식에서는 어떤 상황에서도 전체 배열을 처음부터 끝까지 $O(\log N)$번 읽어야 합니다. 이로 인해 $O(\frac{\log N}{\log N - \log M})$의 속도 향상이 발생하며, 이는 최대 10배(an order of magnitude)까지 차이 날 수 있습니다.

실제로 재귀와 관련된 약간의 오버헤드가 여전히 존재하기 때문에, 기본 케이스(base case)까지 끝까지 내려가지 않고 낮은 재귀 레벨에서 반복적 코드로 전환하는 하이브리드 알고리즘을 사용하는 것이 합리적입니다.

### 동적 계획법 (Dynamic Programming)

비슷한 추론을 동적 계획법(dynamic programming) 알고리즘 구현에도 적용할 수 있지만, 반대의 결과가 나옵니다. 클래식한 *배낭 문제(knapsack problem)*를 생각해 보겠습니다. 양의 정수 가치 $c_i$를 가진 $N$개의 아이템이 주어졌을 때, 총 가치의 합이 주어진 상수 $W$를 초과하지 않으면서 최대가 되는 아이템의 부분 집합을 고르는 문제입니다.

이를 해결하는 방법은 처음 $n$개의 아이템만 사용하여 $w$를 초과하지 않는 최대 가치 합에 해당하는 *상태* $f[n, w]$를 도입하는 것입니다. $n$번째 아이템을 가져오거나 가져오지 않는 경우를 고려하고, 이전 상태를 사용하여 최적의 결정을 내리면 각 항목당 $O(1)$ 시간에 계산할 수 있습니다.

파이썬에는 메모이제이션 재귀(memoized recursion)로 이를 구현할 때 사용할 수 있는 편리한 `lru_cache` 데코레이터가 있습니다.

```python
@lru_cache
def f(n, w):
    # 선택할 아이템이 없는지 확인
    if n == 0:
        return 0
    
    # 마지막 아이템을 고를 수 없는지 확인 (0부터 시작하는 인덱스 주의)
    if c[n - 1] > w:
        return f(n - 1, w)
    
    # 그 외의 경우, 마지막 아이템을 고르거나 고르지 않음
    return max(f(n - 1, w), c[n - 1] + f(n - 1, w - c[n - 1]))
```

$f[N, W]$를 계산할 때 재귀는 최대 $O(N \cdot W)$개의 서로 다른 상태를 방문할 수 있습니다. 이는 점근적으로는 효율적이지만 실제로는 꽤 느립니다. 파이썬 재귀의 오버헤드와 LRU 캐시 작동에 필요한 모든 [해시 테이블 쿼리](../policies/#implementing-caching)를 제거하더라도, 실행 시간 대부분 동안 무작위 I/O를 수행하기 때문에 여전히 느릴 것입니다.

대신 할 수 있는 일은 동적 계획법을 위한 2차원 배열을 만들고 재귀를 다음과 같은 중첩 루프로 바꾸는 것입니다.

```cpp
int f[N + 1][W + 1] = {0}; // 배열을 0으로 채움

for (int n = 1; n <= N; n++)
    for (int w = 0; w <= W; w++)
        f[n][w] = c[n - 1] > w ?
                  f[n - 1][w] :
                  max(f[n - 1][k], c[n - 1] + f[n - 1][w - c[n - 1]]);
```

여기서 다음 계층을 계산하기 위해 이전 계층만 사용한다는 점에 주목하세요. 즉, 한 계층을 캐시에 저장할 수 있다면 외부 메모리에 $O(\frac{N \cdot W}{B})$개의 블록만 쓰면 됩니다.

게다가 정답만 필요한 경우에는 전체 2차원 배열을 저장할 필요 없이 마지막 계층만 저장하면 됩니다. 이를 통해 $W$개의 값을 가진 단일 배열만 유지하여 $O(W)$ 메모리만 사용할 수 있습니다. 코드를 단순화하기 위해 동적 계획법을 약간 변경하여, 이미 고려한 아이템들을 사용하여 정확히 $w$의 합계를 만드는 것이 가능한지에 대한 이진(binary) 값을 저장할 수도 있습니다. 이 방식은 계산 속도가 더 빠릅니다.

```cpp
bool f[W + 1] = {0};
f[0] = 1;
for (int n = 0; n < N; n++)
    for (int x = W - c[n]; x >= 0; x--)
        f[x + c[n]] |= f[x];
```

참고로 이제 단순한 비트 단위 연산만 사용하므로 비트셋(bitset)을 사용하여 더 최적화할 수 있습니다.

```cpp
std::bitset<W + 1> b;
b[0] = 1;
for (int n = 0; n < N; n++)
    b |= b << c[n];
```

놀랍게도 여전히 개선의 여지가 있으며, 이 문제는 나중에 다시 다룰 것입니다.

### 희소 테이블 (Sparse Table)

*희소 테이블(Sparse table)*은 *정적 RMQ(static RMQ)* 문제를 해결하고 일반적인 *멱등 범위 축소(idempotent range reductions)*를 계산하는 데 자주 사용되는 *정적* 데이터 구조입니다. 다음과 같이 $\log n \times n$ 크기의 2차원 배열로 공식화할 수 있습니다.

$$
t[k][i] = \min \{ a_i, a_{i+1}, \ldots, a_{i+2^k-1} \}
$$

쉽게 설명하면, 길이가 2의 거듭제곱인 모든 세그먼트에 대한 최솟값을 저장하는 것입니다.

이러한 배열은 임의의 세그먼트에서 최솟값을 상수의 시간에 계산하는 데 사용될 수 있습니다. 모든 세그먼트에 대해 크기가 동일한 2의 거듭제곱이면서 서로 겹칠 수 있는 두 세그먼트를 항상 찾을 수 있고, 그 합집합이 전체 세그먼트가 되기 때문입니다.

![](../img/sparse-table.png)

즉, 미리 계산된 이 두 최솟값 중 더 작은 값을 답으로 취하면 됩니다.

```cpp
int rmq(int l, int r) { // 반열린 구간 [l; r)
    int t = __lg(r - l);
    return min(mn[t][l], mn[t][r - (1 << t)]);
}
```

`__lg` 함수는 GCC에서 사용할 수 있는 내장 함수(intrinsic)로, 숫자의 이진 로그를 내림하여 계산합니다. 내부적으로 `clz`("count leading zeros") 명령어를 사용하고 이 개수를 32(32비트 정수의 경우)에서 빼기 때문에 단 몇 사이클만 소요됩니다.

이 글에서 이를 언급하는 이유는 메모리 작업 효율성이 서로 다른 여러 가지 구축 방법이 있기 때문입니다. 일반적으로 희소 테이블은 다음 항등식을 적용하여 $i$ 또는 $k$가 증가하는 순서로 반복하는 동적 계획법 방식으로 $O(n \log n)$ 시간에 구축할 수 있습니다.

$$
t[k][i] = \min(t[k-1][i], t[k-1][i+2^{k-1}])
$$

여기서 두 가지 설계 선택지가 있습니다. 로그 크기 $k$를 첫 번째 차원으로 할지 두 번째 차원으로 할지, 그리고 $k$에 대해 먼저 반복할지 $i$에 대해 먼저 반복할지입니다. 즉 $2 \times 2 = 4$가지 구축 방법이 있으며, 다음이 최적의 방법입니다.

```cpp
int mn[logn][maxn];

memcpy(mn[0], a, sizeof a);

for (int l = 0; l < logn - 1; l++)
    for (int i = 0; i + (2 << l) <= n; i++)
        mn[l + 1][i] = min(mn[l][i], mn[l][i + (1 << l)]);
```

이 조합은 메모리 레이아웃과 반복 순서가 아름다운 선형 패스(linear pass)를 만들어내어 약 3배 더 빠르게 작동하는 유일한 조합입니다. 연습 삼아 다른 세 가지 변형을 고려해 보고 *왜* 그것들이 더 느린지 생각해 보십시오.

### 구조체 배열 vs. 배열 구조체 (Array-of-Structs vs. Struct-of-Arrays)

이진 트리를 구현하고 각 필드를 다음과 같이 별도의 배열에 저장한다고 가정해 보겠습니다.

```cpp
int left_child[maxn], right_child[maxn], key[maxn], size[maxn];
```

이러한 메모리 레이아웃, 즉 각 필드를 다른 필드와 별도로 저장하는 방식을 *배열 구조체(SoA, Struct-of-Arrays)*라고 합니다. 대부분의 경우 트리 작업을 구현할 때 노드에 액세스한 다음 곧바로 해당 노드의 내부 데이터 전부 또는 대부분에 액세스합니다. 이러한 필드들이 따로 저장되어 있다면 서로 다른 메모리 블록에 위치하게 된다는 뜻입니다. 요청된 필드 중 일부는 캐시되어 있고 나머지는 그렇지 않다면, 결국 가장 느린 필드를 가져올 때까지 기다려야 합니다.

반면, 이를 *구조체 배열(AoS, Array-of-Structs)*로 저장한다면 노드의 모든 데이터가 동일한 블록에 저장되어 한 번에 가져오므로 블록 읽기 횟수가 약 4배 적어집니다.

```cpp
struct Node {
    int left_child, right_child, key, size;
};

Node t[maxn];
```

일반적으로 데이터 구조에는 AoS 레이아웃이 선호되지만, SoA도 유용할 때가 있습니다. 검색에는 더 나쁘지만 선형 스캔에는 훨씬 유리하기 때문입니다.

이러한 설계 차이는 데이터 처리 애플리케이션에서 중요합니다. 예를 들어 데이터베이스는 *행 중심(row-oriented)* 또는 *열 중심(column-oriented, columnar)*일 수 있습니다.

- **행 중심** 저장 형식은 대규모 데이터셋에서 제한된 수의 객체를 검색하거나 객체의 필드 전부 또는 대부분을 가져와야 할 때 사용됩니다. 예: PostgreSQL, MongoDB.
- **열 중심** 저장 형식은 특정 통계를 계산하기 위해 어차피 모든 데이터를 훑어야 하는 빅데이터 처리 및 분석에 사용됩니다. 예: ClickHouse, Hbase.

열 중심 형식은 서로 다른 필드가 별도의 외부 메모리 영역에 저장되므로 필요한 필드만 읽을 수 있다는 추가적인 장점이 있습니다.
