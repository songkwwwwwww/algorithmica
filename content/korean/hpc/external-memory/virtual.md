초기 운영 체제는 모든 프로세스에 다른 프로세스에 할당된 영역을 포함하여 원하는 모든 메모리 영역을 읽고 수정할 수 있는 자유를 주었습니다. 이 방식은 구조를 단순하게 유지하지만 몇 가지 문제를 야기합니다:

- 프로세스 중 하나에 버그가 있거나 악의적인 경우 어떻게 될까요? 메모리를 통한 프로세스 간 통신을 가능하게 유지하면서 다른 프로세스에 할당된 메모리를 수정하지 못하도록 어떻게 방지할 수 있을까요?
- 메모리 단편화(fragmentation) 문제를 어떻게 해결할까요? 예를 들어 4MB의 메모리가 있고, 프로세스 A가 처음 1MB를 할당받고, 프로세스 B가 다음 2MB를 요청한 상황을 가정해 봅시다. 그 후 A가 종료되어 메모리를 해제하고, 프로세스 C가 나타나 연속된 2MB 영역을 요청한다면 — 현재 분리된 1MB 조각 두 개만 있기 때문에 할당받을 수 없습니다. 프로세스 B를 재시작하거나 중단시키고 모든 데이터와 포인터를 1MB씩 옮기는 것은 좋은 해결책이 아닙니다.
- RAM이 아닌 메모리 유형에 어떻게 접근할까요? 플래시 드라이브를 꽂고 거기서 특정 파일을 읽으려면 어떻게 해야 할까요?

이러한 문제들은 한 번에 하나의 작업만 수행하고 계산을 완전히 제어할 수 있는 GPU와 같은 일부 특수 컴퓨터 시스템에서는 그리 치명적이지 않지만, 현대의 멀티태스킹 운영 체제에서는 절대적으로 중요합니다. 그리고 이 모든 문제들은 *가상 메모리(virtual memory)*라는 기술을 통해 해결됩니다.

### 메모리 페이징 (Memory Paging)

가상 메모리는 각 프로세스에 자신이 연속된 메모리 영역을 완전히 제어하고 있다는 인상을 줍니다. 실제로는 이 영역이 실제 물리적 메모리의 여러 작은 블록으로 매핑되어 있을 수 있으며, 여기에는 메인 메모리(RAM)와 외부 메모리(HDD, SSD)가 모두 포함됩니다.

![](../img/virtual-memory.jpg)

이를 구현하기 위해 메모리 주소 공간은 *페이지(page)* 단위(일반적으로 4KB)로 나뉩니다. 페이지는 프로그램이 운영 체제에 요청할 수 있는 메모리의 기본 단위입니다. 메모리 시스템은 가상 페이지 주소와 물리적 페이지 주소의 매핑을 포함하는 *페이지 테이블(page table)*이라는 특수 하드웨어 데이터 구조를 유지합니다. 프로세스가 가상 메모리 주소를 사용하여 데이터에 접근하면, 메모리 시스템은 페이지 번호를 계산하고(페이지 크기가 $4096=2^{12}$인 경우 주소를 오른쪽으로 12비트 시프트), 페이지 테이블에서 물리적 주소를 찾아 데이터가 실제로 저장된 곳으로 읽기 또는 쓰기 요청을 전달합니다.

모든 메모리 요청마다 주소 변환이 수행되어야 하고 메모리 페이지 수 자체가 많을 수 있기 때문에(예: 16G RAM / 4K 페이지 크기 = 4M 페이지), 주소 변환은 그 자체로 어려운 문제입니다. 이를 가속화하는 한 가지 방법은 *변환 색인 버퍼(TLB, translation lookaside buffer)*라고 불리는 페이지 테이블 전용 캐시를 사용하는 것이고, 다른 방법은 [페이지 크기를 늘려](/hpc/cpu-cache/paging) 세분성을 줄이는 대신 총 메모리 페이지 수를 줄이는 것입니다.

### 외부 메모리 매핑 (Mapping External Memory)

가상 메모리 메커니즘을 사용하면 외부 메모리 유형도 매우 투명하게 사용할 수 있습니다. 현대 운영 체제는 [메모리 매핑(memory mapping)](https://en.wikipedia.org/wiki/Mmap)을 지원하여, 파일을 열고 그 내용을 마치 메인 메모리에 있는 것처럼 사용할 수 있게 해줍니다.

```c++
// 읽기 및 쓰기를 위해 1024개의 랜덤 정수가 포함된 파일을 엽니다.
int fd = open("input.bin", O_RDWR);
// 메모리에 매핑합니다. 크기: 4096, 읽기/쓰기 허용, 변경 사항을 파일에 다시 씁니다.
int* data = (int*) mmap(0, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
// 일반 정수 배열인 것처럼 정렬합니다.
std::sort(data, data + 1024);
// 변경 사항은 결국 파일에 반영됩니다.
```

여기서는 4K 파일을 매핑했는데, 이는 단일 메모리 페이지에 완전히 들어갈 수 있는 크기입니다. 하지만 더 큰 파일을 열면 특정 페이지를 요청할 때 레이지(lazy)하게 읽기가 수행되며, 쓰기는 버퍼링되었다가 운영 체제가 결정할 때(보통 프로그램 종료 시나 RAM이 부족할 때) 파일 시스템에 커밋됩니다.

동일한 운영 원리를 가지지만 반대의 의도를 가진 기술은 *스왑 파일(swap file)*입니다. 이는 실제 RAM이 충분하지 않을 때 운영 체제가 SSD나 HDD의 일부를 메인 메모리의 확장으로 자동 사용하도록 해줍니다. 이를 통해 메모리가 부족한 시스템은 충돌하는 대신 극심한 속도 저하를 겪으며 작동을 유지할 수 있습니다.

메인 메모리와 외부 메모리의 이러한 매끄러운 통합은 본질적으로 RAM을 외부 메모리를 위한 "L4 캐시"로 만듭니다. 이는 알고리즘 설계 관점에서 생각하기에 매우 편리한 방식입니다.
